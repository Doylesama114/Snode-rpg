## 2. 必须遵守的硬规则

1. 规则 100% 遵守斯诺德正文，禁止以“BG3 是这么做的”为由改规则。
2. `core` 不得 import `render` 或 `ui`。
3. UI 不得直接修改 HP/FP/状态/动作预算，必须调用 core 命令接口。
4. 渲染演出不得改变结算结果，必须先结算后播放。
5. 自然语言技能描述只能展示，不能作为执行依据；引擎只执行结构化能力卡。
6. 无法结构化的技能必须标记“未开放”，不得写死特判进 UI。
7. 掷骰必须种子化、逐骰记录，支持回放。
8. 距离规则只允许使用三个函数：
   - `gridDistance`：正交 1、斜角 2；
   - `isAdjacent`：8 格相邻；
   - `combatDistance`：`gridDistance + 高度差绝对值`。
9. 斜角相邻是近战/触及例外，不得把 `isAdjacent` 用于移动步数或远程射程。
10. 所有新规则/口径变更，先改 `战斗系统设计v2.md` 第 22 章，再写代码与测试。
11. 掷骰交互归属：玩家主动能力与玩家豁免=玩家掷骰；怪物豁免/怪物攻击=自动动画。详见《战斗系统设计v2.md》§17.1 与 `docs/rule-decisions.md` §12。

## 3. 改动流程

1. 阅读《战斗系统设计v2.md》对应章节。
2. 确认第 22 章待裁决清单是否有相关未决项；未决项不得擅自实现。
3. **不确定就问**：规则文本不能唯一确定实现方式时，先向项目所有者询问；不得自行猜测技能效果后实现。
3. 写出或更新单元测试，再实现规则。
4. 运行：
   - 核心：`npm test`（snode-combat 内）
   - 类型：`npm run typecheck`
   - UI：Playwright E2E
5. 更新设计文档第 21/23 章的追溯表。
6. 不把未完成的半规则留在 core 中。

## 4. 已知陷阱与教训（来自 v1 归档）

- 旧 v1 效果数据有 964 条 `needs_manual`，不要盲目相信旧 `combat_effects_*` 数据。
- 旧文档与代码曾出现距离口径混用；v2 必须用三个距离函数锁死。
- 旧 UI 曾全量重渲染，v2 渲染层要区分“状态变化”与“演出事件”。
- 旧反应窗口有闭包污染问题；v2 所有弹窗必须绑定 command id，不直接持有可变战斗对象。
- 旧战斗文件未纳入 git 与发布，v2 在验收前先作为独立目录开发；何时纳入发布另行决定。

## 5. 当前开发顺序建议

1. 先定 `data-schema.md` 与游荡者 v1 能力清单。
2. 再写 core 基础类型与三个距离函数及测试。
3. 骰子/RNG/日志。
4. 回合与动作经济。
5. 移动与路径。
6. 攻击命中伤害。
7. 状态系统。
8. 怪物 AI。
9. render/ui 接入。
10. 完整 PVE 切片。
