# 资料库迁移方案（3.1.1）

> 2026-10-22 ｜ 提交对象：合作开发人 ｜ 状态：**方案待评审，尚未写代码**
> 配套记录：`docs/decisions-catalog-migration.md`

---

## 0. 一句话

把旧站的技能、种族、职业数据搬进新项目，改成**一条技能一行、互不影响、整批可回退**的结构，让主持人自己就能安全地更新数据。

---

## 1. 旧站为什么会"更新完又出新问题"

不是 AI 不够聪明，是旧结构本身就容不下局部修改。四个根因：

1. **身份靠名字。** 同名就合并（灵龟守护在猎人那儿有"主动技"和"天赋"两条，被压成一条）；改名就等于删了旧的又加了个新的。
2. **数据挤在大文件里。** `panel_data.js` 4.6 MB、`search-index.json` 4 MB，改一处要重写整份，重写就会碰到别处。
3. **位置即身份。** 技能靠"哪个职业、哪个阶位、第几条"来定位；阶位一调整、技能一删、风格一改，后面的全部错位，表现为字段串位、内容跑到别的技能下面。
4. **原件直接公开。** 技能数据原件放在公网，任何人都能下载。这是旧项目的一个错误决定。

新结构要正面解决这四条。

---

## 2. 三条硬规矩

| 规矩 | 含义 |
| --- | --- |
| **一条技能 = 一个原子** | 每一条技能独立存储。改它的描述、改它的阶位，都不会碰到别的技能。 |
| **身份与位置分开** | 身份由"职业 + 名字 + 形态"决定，永不改变；风格、阶位、顺序只是属性，可以随便动。 |
| **数据只进数据库** | 原件不进货仓、不上公网。数据库是唯一的家，文件只是导入通道。 |

> 关于"原子化到什么程度"：第一版按**技能**成块，不把每个字段拆成独立记录。理由很实在——一条技能的描述、升级行、选项是绑在一起读的，拆成十几个零件后，改一句描述要动十几个地方，出错机会反而翻倍。字段级编辑等后台做熟了再上。

---

## 3. 主持人一次更新会经历什么

```
上传新版文档 → 自动解析 → 只问有疑问的 → 先进后台 → 管理员发布
```

1. **上传**：主持人丢一份新版 docx 过来（整份替换，不用他做增量）。
2. **解析**：系统拆成一条条技能。绝大多数自动通过，拆不动的标红。
3. **确认**：把**有疑问的那几条**逐条推给主持人，用人话问——"这条没读到描述，是漏了吗？""这里原来有'蒸馏工艺'，新版没找到，是删了吗？"
4. **入库**：先进"仅后台可见"，玩家看不到。
5. **发布**：管理员勾选后对玩家可见；发布即生成一个版本，可以整批回退。

> 这条流程的意义：**主持人不需要懂 AI**。他要做的只有"丢文件、回答几个问题、点发布"。

## 4. 一条技能长什么样

分四组字段——**身份永不改，位置随便动**。

| 组 | 字段 | 说明 |
| --- | --- | --- |
| **身份** | 技能 ID、名字、所属职业、形态 | 一旦生成，除非"改名=新技能"，否则永不改变 |
| **位置** | 风格、阶位、顺序 | 可随意调整，不影响身份 |
| **规则** | 关键词、施展时间、距离、持续、疲劳消耗、标识（彩色圆点）、额外条件、前置条件 | 从文档解析，解析不了的保留原文 |
| **正文** | 描述、升级行、选项（抉择）、附件（召唤单位属性块 / 加工方案） | 附属内容挂在这条技能下面，不独立成条 |
| **状态** | 草稿 / 后台可见 / 玩家可见 / 已停用 | 两段式可见性的核心 |
| **溯源** | 来源文档、首次出现批次、最后修改批次 | 出问题时能查"这条是哪一版加进来的" |

示例（法师的一条技能）：

```json
{
  "技能ID": "mage-mengji-01",
  "名字": "强力猛击",
  "所属职业": "法师",
  "形态": "主动技",

  "风格": "斗争",
  "阶位": "三阶天赋树",
  "顺序": 12,

  "关键词": ["战技", "近战攻击"],
  "施展时间": "主要动作",
  "施展距离": "2米",
  "持续时间": "立即",
  "疲劳消耗": "3点",
  "标识": [{ "颜色": "红", "分组": 0 }],

  "描述": "……原文照录……",
  "升级行": [{ "等级": 5, "内容": "……" }],
  "选项": [],
  "附件": null,

  "状态": "后台可见",
  "来源文档": "基础职业-法师.docx",
  "首次出现批次": 7,
  "最后修改批次": 9

```

## 5. 四种"变化"分别怎么处理

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| **同名不同形态**（灵龟守护：主动技 / 天赋） | 存成两条，靠"形态"区分 | 旧站按名字合并，这正是丢来源的根源 |
| **改名** | 算新技能；旧的那条自动停用并在原位置留占位 | 你们确定"改名一般当新技能处理"，那就别猜 |
| **删除** | 停用 + 留占位，玩家侧显示"原文已移除" | 玩家角色卡上可能正挂着它，真删会凭空少一条；留占位才能回档 |
| **移动**（阶位调整、风格变更、顺序切换） | 只改位置字段，身份不动 | 这是旧站错位的重灾区，分开了就不会连带 |

## 6. 版本与回退

- **一次发布 = 一个版本**（"10 月 22 日这版"）。不做每条技能各自版本号——那样没法回答"线上到底是哪一版"。
- 每次发布留一份**不可变快照**，回退就是整批退回上一版。
- 单条技能保留"首次出现批次 / 最后修改批次"，用于追责和查来源。

---

## 7. 谁能看见什么（两段式）

| 阶段 | 玩家 | 主持人/管理员 |
| --- | --- | --- |
| 导入后 | 看不见 | 看得见，可逐条检查 |
| 发布后 | 看得见 | 看得见 |

- **图片走同一套**：主持人做的进阶效果卡、道具卡、装备卡，先入后台，需要给玩家看时再勾选发布。
- **数据质量问题不进玩家前台**：解析失败、字段缺失这类，只在后台标红，由管理员修。玩家侧最多看到"这条内容暂不可用"。

## 8. 一期范围

**做：**
- 18 个职业的技能（先以法师跑通，它是 422 条、结构最脏的一个）
- 30 个种族 + 96 条种族天赋（已有结构化数据）
- 神圣领域、通用天赋树（同一套结构）

**不做（后续批次）：**
- 装备、物资全量
- 玩家侧的浏览界面（由你敲定）
- 登录、权限体系

**明确不属于 3.1.1：** 新手引导。
