### 3.3 核心问题和解决方向

1. 上传、学习、技能树、搜索使用不同资料，更新不一致：改为同一规则发布包与完整详情入口。
2. 同名技能按名称合并，丢职业与阶位：名称仅检索候选，真正绑定来源条目AbilityEntry。
3. 特殊专长的跨职业技能丢失来源、成长或关键属性：获取、摆放、成长、属性、费用、占栏分别保存。
4. 召唤物详情只剩摘要：模板和全部固有能力作为可继续读取的关联，四个入口共用渲染器。
5. 旧存档依赖角色名和槽位：云端使用不可变characterId；名称可改，槽位只作来源定位。
6. 上传或恢复历史重复发资产：钱包库存由资产服务持有；历史声明审批后入账。
7. 页面计算与手工状态耦合：来源记录、纯规则、授权操作分开；未知不填0，汇总值不覆盖来源池。
8. 用构造样例冒充全量验收：结构、关系、规则、权限、事务、真机分别记录证据。

## 4. 总体架构与共用数据模型

### 4.1 四类对象分开

| 对象 | 含义 | 归属示例 |
| --- | --- | --- |
| 共用定义 | 人人共用、可版本化的规则资料 | 职业、技能、物品、领域；资料发布包 |
| 持久实例 | 某角色的选择、获取与当前值 | 职业进度、能力UID、护盾来源；角色文档 |
| 服务与资产 | 登录归属、修订、团关系、真实库存 | owner、revision、钱包、物品实例；服务 |
| 战斗运行状态 | 本场行动、效果及事件 | 动作余额、反应窗口、蓄能进度；未来战斗状态 |

**新角色新增数据记录，新职业新增定义关系，不新增人物程序class。** 既有机制内的新技能、阶位和领域主要通过数据扩展；全新机制仍可能需要Schema、处理器和验证。

~~~text
原始资料 + 已确认修订
          ↓ 提取、规范化、验证
不可变发布包（定义 + 全文 + 资源 + 旧映射）
          ↓
公开查询               纯规则计算
                           ↓
本机建卡/管理输入 → API提交编排 → 角色/快照/流水/资产
                           ↓
                    授权投影与操作结果
                           ↓
                    未来战斗输入快照
~~~

### 4.2 建议模块

| 位置 | 职责 | 依赖边界 |
| --- | --- | --- |
| packages/model（新增候选） | 领域结构、精确引用、正文、基础Schema及同源类型 | 无React、DOM、Fastify、DB |
| packages/catalog（新增候选） | 发布资料、关联、源顺序、索引读取 | 不持有角色、账号、资产 |
| packages/rules（新增候选） | 支持范围内的计算、条件、操作预览 | 纯计算，不直接写库或调用市场 |
| packages/contracts（已有） | HTTP请求、响应、错误 | 不能以传输视图替代完整角色 |
| packages/db（已有） | 元数据、文档、历史、命令、资产事务 | 双方评审后增加迁移 |
| apps/api（已有） | 身份授权、重算、事务、投影 | 不信前端最终结果 |
| apps/web（已有） | 资料、建卡、编辑、草稿、反馈 | 延续管理协议，按模块接入 |

包数量可按实际共用关系调整。工作区已覆盖apps/*、packages/*，根dev却只监听现有四项；新增包时补监听、构建和验证。

### 4.3 身份、版本与未知值

DefinitionRef为id＋revision，RuleReleaseRef为id＋manifestHash。实例UID区分同一角色的同名持有、来源池与选择；跨角色引用需带characterId。角色修订、结构版本、视图版本、本机草稿版本分别计数。

发布缺失或引用版本错误应明确报错，不取latest代替。资料变更产生新revision/release/hash；历史角色不因最新资料静默重算。索引可重建，定义与正文是读取权威。

Recorded<T>区分known、unrecorded、unresolved：已知0不等于缺失，未知来源可以追溯原始输入。派生结果区分ready、needs-decision、unsupported并给依据。

### 4.4 完整角色文档

当前CharacterDocument候选有31项顶层字段，按业务分组如下：

| 字段组 | 字段 | 用途 |
| --- | --- | --- |
| 基础 | schemaVersion、characterId、ruleset、profile、race、background | 结构版本与角色选择 |
| 职业选择 | progressions、domains、choices、mainUnlockedTiers | 主/子/附赠职业、领域、选择、实际解锁 |
| 获取持有 | acquired、abilities、features、recipes、knowledge、mechanisms、slotBonusGrants | 获取途径、能力、特性、图纸、知识、机制和容量 |
| 限制 | learningRestrictions | 遗忘或拒绝授予后的永久禁学 |
| 属性成长 | attributeFacts、proficiencyGrants、hpGrowth、statOwnership | 加成来源、实际升级收益、上限归属 |
| 资源状态 | resources、learningSession、manualPools、manualStatuses | HP/FP、XP/SP、学习标识、来源池与状态 |
| 关联 | companionIds、equippedAssetLinks | 持久单位及真实资产引用 |
| 依据 | requirementFacts、legacyInputFacts、issueRefs | 条件、历史原文和待核对问题 |

文档之外，生产服务封装保存ownerUserId、revision、lifecycle、timelineId、campaignAssignmentId和系统时间。T07的CharacterRecord尚缺ownerUserId，应补服务结构，不另建第二套角色模型。

历史上限可按statOwnership暂保留原记录；确认完整成长后再明确转为派生。手工护盾、临时生命、状态按来源UID保存，剩余量不能在读取时重生成满额。空sourceRecordId不能自动证明拥有手工编辑权。

### 5.2 三层能力结构

| 层级 | 保存什么 | 为什么需要 |
| --- | --- | --- |
| AbilityDefinition | 共用正文、效果语义片段、成长规则、关联模板 | 同效果可共享完整内容 |
| AbilityEntry | 具体来源表、职业、阶位、风格、获取规则、sameNameGroup | 同名在不同职业可以不同阶位 |
| LearnedAbility＋AcquisitionRecord | 实例UID、真实条目、获取途径、摆放、成长、关键属性、栏位、选择、支付与证据 | 保留某玩家实际如何获得 |

例如特殊专长获得另一职业技能：界面可以放在本角色能力区，但仍指向真实来源Entry；成长等级和关键属性按该获取规则绑定。既不能改成主职业来源，也不能直接套用源职业等级。

规则已明确：初始技能和初始天赋归一阶；有些旧职业缺tier/style属于遗漏。仅针对识别为相应初始授予的记录修复，不把任意未知技能都补成一阶，也不把所有一阶技能免费授予。风格依据原文补齐，未知不能统一写“通用”。

### 5.3 职业、阶位和领域的可扩展结构

ClassDefinition引用关键属性候选、成长规则、能力表、起始授予、选择及进阶候选。ClassProgression记录角色内UID、main/sub/gift、baseClass、level、keyAttribute、advancement和选择途径。

等级与阶位不同：TierDefinition保存名称与顺序，具体解锁由规则关联；不硬编码七阶、固定职业名单或等级上限。进阶后保留baseClass与原进度UID，按基础职业等级成长。

DomainDefinition引用deity、适用职业、能力表、初始授予和modeRef。DomainSelection绑定ownerProgressionId及正式选择。锁定神祇无表时保留开放状态，不能生成虚构领域技能。新增神祇或领域不修改牧师页面中的固定分支。

属性、熟练项、资源、伤害类型、状态、语言、标签、装备位等采用注册定义。学习色彩标识、语义字体颜色、领域属性、D8色彩骰分别表达，不能因颜色相同而混成一套机制。

### 5.4 召唤物与单位

EntityTemplate至少保留完整正文、分数挑战等级、基础值、固有能力引用、变体及来源。原表固定AC、HP、攻击加值先保留含义，不能擅自改为属性推导。

- 模板固有技能是独立能力，不能因为同名就混入角色可学习技能列表。
- 多个召唤物、不同等级变体、随机表和续行说明都要完整可读，不能只取第一张表。
- PersistentUnitRecord记录长期契约或伙伴；CombatEntityState未来记录本场位置、归属、当前资源与效果。
- 两只同模板单位使用不同实体ID，当前HP与状态互不覆盖。
- DerivedActorSnapshot引用确切角色/单位修订、规则包和装备修订，向战斗提供解析上下文。

### 5.5 实施方法与验收

按“来源清单 → 稳定ID注册 → 原始提取 → 规范定义/全文 → 关系与差异核对 → 发布”推进。LegacyMapping保留原文件、旧ID、旧别名、来源位置与目标Ref；歧义保留多候选，不猜一个。

T07样例曾有38项目录载荷差异，通过独立评审投影解决：30项正文旧链接、6项职业及2项领域中的样例注记。投影保留8份注记和30份版本正文链接，**原样例不改，投影不作为正式发布包**。其余55个已知kind记录仍主要是元数据/文本，正式建卡前要补足相应载荷与规则。

验收应证明：各来源去向明确；引用存在且kind正确；阶位、风格和来源保留；全文及资源无遗漏；角色内实例不靠名字绑定；新增已支持机制的职业/阶位/领域可用数据表达。目录可读、角色可计算、战斗可执行分别声明。

## 6. 规则与世界观文档迁移（区块2）

### 6.1 复用范围

保留原DOCX/XLSX正文、世界观、图片、规则表格和章节顺序；复用已验证的段落、字体语义、表格、续行提取算法。旧help页面的导航、搜索体验可作参考，HTML脚本和页面布局应转为独立React功能。

### 6.2 内容与依据结构

ContentDocument由有序块组成：paragraph、table、asset、definition-link。InlineRun保留文本、强调、展示颜色和明确的语义颜色；TableCell保留rowSpan、colSpan、背景和文字；图片以contentHash引用，另带mediaType与alt。

来源登记保存文件哈希、仓库基线和定位。SourceEvidence标记未审核、已核实或冲突，并引用确认记录和问题。RuleDecision保留问题、答复、适用范围、修订和被替代关系。

原始文件与规范解释同时保留：DM补充或勘误不直接改掉原始资料。正文能够显示解释及依据，规则计算引用已确认片段。

### 6.3 规则可信度

| 来源 | 使用方式 |
| --- | --- |
| 冒险者基础规则.xlsx | 用户指定的现行基础规则主要来源；歧义逐项核对 |
| 原始职业、种族、背景、技能表 | 内容和语义来源；提取并不自动意味着机制确认 |
| 已复核的用户/主持人答复 | 保存适用范围、更正及来源冲突；不是无条件覆盖全文 |
| 旧战斗设计手册公式 | 不可信，暂作历史参考，不能直接进入计算 |
| 网页、索引、代码、战斗原型 | 交叉对照及兼容依据，不自动覆盖原规则 |
| 本计划及构造样例 | 软件设计和验证场景，不是新增游戏规则 |

已发生的答复更正必须沿用最后结论，例如临时生命/疲劳多来源取最高，超杀即死包含等于负上限；旧答复仅留在追溯历史。

需要叙事或DM判断的条件记录为RequirementFactRecord，包含reported/confirmed/disputed、范围和裁决引用。玩家自行填写故事不等于已获得规则收益。

### 6.4 防遗漏和发布

每个原始段落、表格、图片都应有覆盖映射。已结构化完整替代的片段可去重；未覆盖片段按原顺序保留展示，不能因无法解析就舍弃。

渲染只接受受控内容块和安全资源，不执行原HTML脚本。发布清单固定定义Ref、资源哈希、源清单哈希及修订依据；旧链接经映射跳转。验收按片段、表格、资源及尾部说明核对，不能只核对技能名称或标题数量。

## 7. 查询、技能树与完整详情（区块3）

### 7.1 可以复用什么

保留职业/阶位/风格分类、来源顺序、别名搜索和多候选展示的有效体验；复用已有完整正文资料。旧页面查询函数及简化技能库应重新接入同一发布目录。

### 7.2 查询方法与接口方向

公开API提供发布列表、指定release搜索与筛选、精确定义/Entry详情、关联正文/单位读取和旧引用解析。请求与结果都明确版本，分页保持稳定源顺序；找不到版本、错误Entry上下文、未收录内容分别报错。

SearchIndex保存normalizedName、aliases、kind、sourceEntryRef、filterRefs、sourceOrder与必要摘要，发布时生成。它不保存第二份可编辑技能正文。名称相同展示来源与阶位后供选择，不能静默选首项。

未结构化机制的资料仍可按text-only完整展示，但明确尚不可自动计算。查询支持范围不足时显示清单边界，不能返回空结果并暗示不存在此技能。

### 7.3 共用详情组件

资料库、学习面板、主职业技能树、已学技能详情统一使用：

~~~text
精确Entry/实例上下文
  → AbilityDefinition
  → 完整ContentDocument
  → 关联EntityTemplate及变体
  → 模板全部固有能力正文
~~~

组件保留长正文、表格、颜色、换行、图片和附注；关联可继续展开，循环引用和加载失败明确处理。只给召唤物一个标题或属性摘要不算解决原问题。

已学能力详情额外显示实际获取来源、成长等级、关键属性和阶位；正文来自同一目录，不由面板另写一份效果。缺来源时保留原文，并显示待核对入口。

验收至少覆盖普通能力、同名异来源、领域或跨表技能、含多项固有动作的召唤单位。既检查数据关系，也在实际页面确认四个入口展示一致且完整。

## 8. 建卡与规则计算（区块4、5）

### 8.1 保留流程，重做提交与计算

保留八个业务节点：职业 → 起始特性 → 种族 → 属性 → 熟练项 → 个性背景 → 装备 → 确认角色。次序可按试用调整，必需选择不得省略。

旧页面逻辑可作算法和行为对照；只有经规则核对的部分适配成纯函数，不能照搬旧计算公式。职业、种族、领域、宗主、龙种、体型、专业、语言、契约生物、背景戏法、装备组等条件选择来自定义，而不是页面职业名称分支。

### 8.2 受控输入与选择

BuildInput提交固定规则包、资料选择、关键属性、种族加成前的购点原始值及受控选择。characterId、owner、最终上限、等级、余额由服务生成或计算，客户端不直接声明。

新选择先用ChoiceSubmission {clientChoiceKey, choiceDefinition, value}；ChoiceUse区分既有记录和本次临时键。服务检查数量、候选、互斥和重复后生成ChoiceRecord UID，再将正式ID交给内层规则。

切换职业或种族后重新检查受影响选择，保留可解释的无效输入并提供修改入口，不能静默丢弃或把非法选择带进最终角色。

### 8.3 纯计算和校验分层

结构Schema、引用关系、游戏条件、当前权限、事务分别校验。前后端同一资料版本和输入使用同源规则；前端预览方便用户，服务器提交时仍需重新计算。

首批计算覆盖属性购点与种族修正、关键属性、熟练、起始特性、背景、HP/FP、基础防御、移动、负重、技能/天赋栏位、装备与货币。具体购点数值、物价和兑换率以来源为准，不在设计中发明常量。

成长结果包含来源、使用的职业进度与属性依据。临时属性、永久属性、记录上限、升级时获得的HP/FP分开处理，避免更新属性后改写全部历史成长。

### 8.4 预览到正式创建

~~~text
本机草稿 → 必需选择完成 → 规则预览
      → 用户接受当前方案 → 冻结创建命令
      → 服务授权/重算/比较方案
      → 角色＋起始资产＋历史＋回执一次提交
~~~

OperationPreview区分ready / needs-selection / needs-decision / unsupported，给出费用、收益、容量与问题。只有实际支持且合法的组合能ready。

planHash覆盖选择、规则、费用、收益及政策等语义输入，排除随机UID和时间。提交时重算，方案改变需重新预览，不能接受旧费用再按新费用扣款。

创建前没有角色ID，创建命令结果查询不能依赖尚不存在的角色路由。客户端先持久保留冻结命令；结果不明核实原commandId。

### 8.5 起始资产仅生成一次

建卡一次事务创建角色revision1、独立钱包/库存、起始授予、装备/容器、选择与获取记录、不可变快照、审计及回执。初始资源与装备分配按内部授予/分配流水关联，不能产生角色却漏装备。

双重防重：

- 同一可信principal＋commandId只执行一次；同键不同内容拒绝。
- 同一principal＋buildDraftId只物化一个角色；换命令ID重复提交同份建卡也不能多领起始资产。

第二种重复返回已有角色的授权定位或build-already-created，不将旧回执伪装成新命令成功。货币采用注册币种和明确最小单位的安全整数；换算、随机起始物资、叙事奖励须有规则或审批依据。

首个闭环建议选人类战士，但现有构造样例不等于已证明其合法。先补齐该组合真实种族、背景、选择、物品、币种载荷；之后覆盖龙裔、可选体型、法师学徒、奇械师图纸、牧师领域、召唤师契约和谋士等分支。

## 9. 角色面板、草稿与云端编辑（区块6、7）

### 9.1 复用目标项目已有核心

目标本地已有contracts、validation、editor、draft、adapter与CharacterWorkspace候选。建议继续复用这些正确协议，新增完整文档适配和真实CharacterService，而不是重写整套编辑器。

已有六个界面区域：资料经历、当前数值、成长能力、装备物品、手工状态、历史快照。目前实际实现重点是资料、已注册数值和只读历史；其余是接入位置，不能报告已经可用。

| 显式保存＋约600ms本机草稿 | 正式记录与未保存输入分开 |

### 9.2 管理视图不是完整角色

ManagementView v1是授权投影，保持严格字段：

~~~text
viewSchemaVersion, characterId, characterRevision, lifecycle,
profile { displayName, story },
editableProfileFields,
numericFields [{ fieldRef, label, value:number|null, editable }]
~~~

UpdateManagementCommand保持commandId、characterId、expectedRevision、submittedDraftVersion、edits；edits只含set-profile、set-number、clear-number。CommitReceipt保持commandId、submittedDraftVersion、view。

不要直接向严格v1塞入issues、quality、库存或新业务命令。用独立Workspace包装DTO组合ManagementView、RuleView、RecordAssessment、能力和资产投影。DM若只能管理状态而不能读故事，提供独立StateManagementView/Command/Receipt；不能以空字符串掩盖必需字段、伪装成同一v1。

CharacterDocumentAdapter完成完整文档校验、授权投影与注册编辑的应用。当前本机服务存投影仅用于演示，生产必须存完整CharacterDocument。

### 9.3 字段边界与数值

首轮普通编辑建议名称、故事、hp.current、fp.current。XP/SP、等级、归属、钱包不能开放任意set-number。临时生命、护盾、力竭按来源UID操作，不能直接提升演示中的hp.temporary/shield.manual/exhaustion.manual汇总字段为生产写口。

保留负HP；是否超过资源上限、具体整数要求依字段规则判断。未知显示为未知/待核对，清空与数值0分别提交。非法输入能留在草稿，不改为0再保存。

现有软件预算暂为ID128、名称256、故事65536个JavaScript UTF-16代码单元，待D12确认。标准Schema maxLength的Unicode计数与此不同，不能直接替代；使用同源预算检查并保留原文，不截断。名称不能仅空白，故事允许空字符串。

### 9.4 云端保存与冲突

保存前冻结commandId、expectedRevision、submittedDraftVersion和edits，先保存本机检查点，再发送。回执必须逐项匹配冻结命令和当前会话；保存成功仅确认已提交版本，不丢保存期间新输入。

适配现有编辑器的建议：有效非空管理命令被接受时，即使写回相同值，也产生下一revision、快照和审计；同键重放不再增版。UI无改动时可不派发。

expectedRevision低于当前值返回409冲突，保留输入再比较；高于当前值返回422 invalid-base-revision，不能送进要求“最新版本更高”的acceptConflict流程。

读取失败、正式提交失败、本机保留失败分别展示。结果不明不是失败重试新命令，也不能直接丢草稿离开。正式云端成功后跨设备能读已保存版本，本机未保存输入首轮仍不跨设备。

## 10. 成长、技能学习与永久限制（区块5、6）

### 10.1 重做原则与主要数据

保留经核实的升级、兼修、解锁、学习和放弃语义及原说明。旧panel_engine的分散职业分支改为受控规则和操作计划。

ClassProgression记录职业进度；GrowthAward冻结每次升级实际HP/FP及属性依据；MainTierUnlock保存支付与裁决；AcquisitionRecord保存获取/选择/支付/顺序；LearnedAbility保存独立绑定；LearningRestriction保存永久事实。特性、图纸、知识和机制分别持有，不全部塞进技能数组。

GrowthBinding、KeyAttributeBinding、SlotBinding与StyleParticipation各自解析。放在某职业栏中，不自动意味着随该职业成长；免费不自动免栏；共享开阶不意味着共享等级。

### 10.2 已核对规则对模型的约束

| 规则 | 当前结论 | 数据和实现处理 |
| --- | --- | --- |
| 建卡及熟练 | 继续现有规则；通常不得突破熟练度上限，奥秘按指定子项选择 | 受控Choice与有来源ProficiencyGrant |
| 子职业首级 | 获取熟练、初始专长和起始特性，不获取首级/当次升级HP、FP；后续升级才获取升级量 | 获取与成长奖励分开，不能统一调用主职业首级公式 |
| 体质变化 | 永久变化仅影响首级对应收益，不重算历史升级量；临时变化不改上限，除非明示 | 首级依据与GrowthAward冻结值分别处理 |
| 色彩标识 | 保留到下一次游玩开始前；奇械师旧表未更新 | LearningSession；旧费用按版本保留，消耗/替代边界待定 |
| 技能点余额上限 | 仅主1；主＋子2；主进阶无子2；主进阶＋子3；主子都进阶4 | 容量规则，不把它当技能栏总数 |
| 免费免栏 | 已明确列举的初始能力及特殊授予按相应政策免费、免栏 | 记录acquisitionRule与slot政策，不泛化到所有一阶 |
| 天赋栏 | 主、子、通用天赋同阶共用槽位 | 按阶位建立共享池；通常5格，例外额外容量另记 |
| 开阶 | 所有子职业跟随主职业实际已开启阶位；牧师通用及领域同时开启 | 不按子职业低等级再次锁阶；等级成长仍独立 |
| 风格顺序 | 按学习顺序；起始建卡不定顺序，战斗心得可定，跨职业获取不定顺序 | acquisitionOrder及路径规则派生，不直接写第一风格 |
| 风格数量 | 免费初始、天赋计入；跨职业按具体参与政策；未习得为0 | 顺序与计数分别计算；并列极值仍属于该极值 |
| 兼职条件 | 两职业间可否兼职不一定互相对称 | 按有方向的兼容关系检查 |
| 镜子大师 | 随主职业成长；忽略前置不免色彩标识，对立学派仍阻止 | 获取规则明确例外，不设置全局ignore-all |
| 进阶 | 保留基础职业及其等级，任选三条途径，实际一职业进阶一职业 | 原progression上追加advancement引用 |
| 遗忘 | 不返技能点；同名跨来源永久禁学 | 同名规则组＋不可逆限制，来源Entry仍分别保存 |

遗忘规则不能未经依据自动扩展到所有特性、图纸和知识。风格删除后的顺序、额外遗忘/替换费用、附赠职业容量、重复机制授予等尚未充分确定，按实际操作依赖阻塞。

### 10.3 自动授予与满槽决策

已确认“召唤隐形战仆”在15级自动获得且占栏。满槽时提示放弃现有技能之一，或放弃本次习得；两种放弃都涉及永久禁学，必须清楚显示后果。

以GrantOffer表示真实成长事件产生的待决授予，不由客户端任意提交“免费技能”。受控decision取接受/替换/拒绝，服务复核容量、来源和风险确认。

LearningRestriction区分：

- permanently-forgotten：持有过，记录原能力UID及formerEntry。
- permanently-declined-grant：未持有，记录declinedEntry及grantRule，不造一个虚构持有实例。

同一成长/授予事件使用稳定逻辑防重键，不能改commandId或规则revision就重复领取。同一旧实例不能在一项复合计划里被替换两次。

### 10.4 操作计划与验收

B4已有20类受控操作候选，涵盖职业成长、学习/遗忘/替换、能力放置、手工资源/状态、装备/卸装/容器与授权奖励调整。它们是契约方向，尚未全部实现。

通用流程：单一业务意图 → 当前版本及权限检查 → 费用/条件/收益/容量预览 → 用户接受 → 服务器重算 → 一次事务提交。禁止任意JSON Patch、客户端最终上限、伪造付款或免费标记。

学习前同时检查已持有的同名规则组和永久禁学；历史重复实例先保留待核对，不按名字自动合并。

验证需覆盖跨职业绑定、同名来源、免费占栏、额外槽位、成长冻结、永久限制、重复领取、未决费用、历史恢复不绕过限制。具体技能战斗效果不在本批实现范围。

## 11. 装备、库存与历史资产（区块1、6，与3.2协作）

### 11.1 可复用与重做边界

旧装备分类、起始装备组、物品说明、图纸语义可保留。旧数组中的数量、金币和装备状态不能直接成为新云端资产权威。

ItemDefinition是共用资料；AssetInstance是某角色真正拥有的物品；钱包和库存由3.2管理。CharacterDocument仅保存AssetLink，包括assetInstanceId、equipmentSlotRef和expectedAssetRevision。

角色面板展示资产服务的当前投影。计算装备收益前确认当前归属、定义、状态与版本；角色快照携带的旧引用不证明现有所有权。

### 11.2 配装与并发

装备/卸装、容器变更及会影响角色派生的资产操作由统一提交入口完成。角色revision之外，还需AssetBasis记录受影响物品、容器、旧装备位和版本，因为资产可在角色版本未变时被交易或修改。

未入团允许持有、读资产及配装，不开放市场和跨角色转移。物品使用/消耗需要明确用途、权限和规则，不能靠通用装备接口任意扣物品。

金币与物品不得采用最后写入覆盖。若角色、资产共用PostgreSQL，建议共同事务；若不同数据库，先设计耐久协调和失败恢复，不能用前端连续两个HTTP请求冒充原子提交。

### 11.3 历史资产入账

迁移只产生LegacyAssetClaim，记录原币种/数量、原物品文本、可能定义、来源定位和claimRevision。批准前仅展示“待核对”，不参与可交易余额；旧档配装也不能提前产生权威属性加成。

入团后的实际DM按当前权限确认固定claim集合和版本。审批、钱包/库存流水、物化映射、审计与命令结果同事务；修改声明后不能继续复用旧审批。

同平台已有assetInstanceId须核对当前服务，合法引用不重新发物。跨角色复制不能让同一物品实例双重拥有；文件中的owner、余额、交易标记不是授权证明。

历史快照恢复只恢复允许的角色事实，不回滚钱包、库存、交易、所有权或重新领取初始装备。资产纠错需要独立有权限的流水，不能用角色JSON恢复代替。

## 12. 旧档导入、UID与备份交换（区块7）

### 12.1 可保留的基础

复用character_io.js中原始值保留、负数读取、元数据、visibleBaseline和UID思路，以及多候选识别和预览体验。旧上传页、槽位身份、按名自动绑定与隐式发资产需重做。

旧链路曾出现技能UID往返保住、天赋仍被误判“基线变化”的问题。因此技能、天赋、图纸都要经过同一UID和基线协议；阶位归一化不是完整解决办法，还应区分正文编辑、来源变化、实例删除和元数据损坏。

### 12.2 格式与选择对象

旧全量JSON实际形状：

~~~json
{
  "meta": {
    "version": "1.0",
    "exportedAt": "...",
    "charCount": 3
  },
  "saves": {
    "char_某角色_slot1": "{\"...\":\"保存内容是JSON字符串\"}"
  }
}
~~~

charCount是保存条目数，不是去重后的角色数；旧键char_<name>_slotN中名称可含下划线。单个损坏条目保留问题，其他条目仍可预览；根结构损坏才作为整文件错误。

选择顺序为文件 → 记录/工作表 → 角色区域 → 槽位。一个文件可含角色和笔记两表，一张表可含多个角色区域；不能直接取首表、最大表或扫描全部单元格合并成一个角色。

### 12.3 Excel兼容方法

| 情况 | 应采用的方法 |
| --- | --- |
| 普通旧档无隐藏元数据 | 按模板特征、标题和区域识别；允许人工选择 |
| 数字与负数 | 保留数值及原始表示；不只匹配正整数 |
| 公式 | 优先读取可信缓存值，缺缓存保留未知与原公式，不填0；不承诺计算全部Excel公式 |
| 字符串 | 支持共享字符串、内联/富文本、XML实体如`&amp;`；不靠脆弱正则拼XML |
| 多表与笔记 | 明确表/区域归属，按关系ID找到正确内容 |
| 行数溢出 | 元数据和备份保留未写入可见区域的条目，不因模板格数删技能 |
| 新旧元数据 | 旧_SNODE_META读取版本1～3，现有写出为3；未来版本明确提示未支持，原内容保留 |
| 第三方编辑 | 检查可见区域与基线差异；元数据丢失时降低为可见信息导入并给损失报告 |

四份真实档案只做过只读结构探查：其中有两表档案、无元数据档案、负数和17个带缓存公式。**没有完成真实转换或往返验证。** 这些文件应在B5建立脱敏测试夹具，逐一验证，不能以构造单表替代。

### 12.4 UID与差异识别

ImportedSourceRecord保留来源版本、字节哈希、工作表/区域/槽位和旧角色标识；LegacyInstanceMapping保存原实例与新实例对应。

原UID可信且可见值符合基线时保留UID及来源。首次无UID导入建立并持久保存映射，之后不能按每次读取、数组顺序或技能名称重新生成。

重复UID视为错误或待决，不自动合并。仅修改说明不等于换技能；删可见行不等于一定遗忘；元数据损坏不等于玩家放弃。明确复制角色时重映射内部实例及引用，保留旧来源追溯，不能复制他人资产所有权。

文件哈希用于证明内容版本，不是唯一角色身份。更新同一旧角色、换文件名、第三方另存、重复上传都要核对lineage和物化映射，避免新文件哈希导致重复奖励或资产入账。

### 12.5 待核对保存与补选

未知字段进入LegacyInputFact，保留原文、现值、原UID、可能匹配与issueRefs。允许正式保存待核对角色；受影响的自动操作阻塞，无关资料编辑可继续。

补选来源使用issueId＋能力UID定位，联动acquisition、tier、growth、keyAttribute、slot和style等绑定。它是纠正事实，不是重新学习，不扣第二次费用、不再领取初始收益、不退款。

导入旧档中的XP/SP/等级属于待核对事实，不能因为记录数字存在就自动变为可消费或可领取奖励。更新云端既有角色必须验证当前权限和expectedRevision；文件内characterId/owner/revision不能自行授权。

### 12.6 新版备份与往返承诺

建议新JSON备份kind为snode-character-backup、formatVersion为1，保存完整CharacterDocument、来源、已声明资产、不可逆限制和未识别事实。它是角色语义备份，不是任意原Excel宏、图表、二进制及排版的完整恢复。

备份不得包含令牌、登录权限或机器本地绝对路径冒充便携附件。恢复仍走预览、授权、校验和资产核对，不能直接PUT整份JSON覆盖当前数据库。

XLSX按明确模板及约定元数据输出可读字段和角色语义；新版是否升级元数据版本需共同确认。第三方工具删除元数据后只能承诺可见信息恢复，必须给出损失清单。

验收至少覆盖“新平台保存→导出→重新导入”JSON与约定XLSX、多表、多槽、同名、跨职业、技能/天赋UID、溢出行和未知事实。生成文件、触发下载和用户实际保存成功分别报告。

## 13. 权限、存储与提交事务（与3.2共用）

### 13.1 权限从真实身份产生

3.2提供verified principal及对象/字段策略，3.1用当前策略组织投影和操作。前端editable、contextKey、导入文件中的owner或“已验证”标记都不是服务授权。

| 场景 | 建议服务行为 |
| --- | --- |
| 公开资料 | 只返回已发布资料；不混入私有角色 |
| 未入团角色 | owner管理自己的角色及允许配装 |
| 已入团角色 | 按真实团关系、角色和字段范围授权 |
| DM状态维护 | 用受限状态投影，不默认开放私有故事 |
| 资产批准 | 仅当前团实际有权DM，核对claim版本 |
| 命令结果/历史查询 | 每次重新授权；失去权限后不泄露旧完整回执 |

可读、可写、可执行成长、可批准资产分别表达；拥有某项管理权限不意味着可修改所有数字或撤销永久限制。

主要API沿用现有/api前缀，以下是对应契约候选中的入口，尚未实现：

- 公开资料：GET /api/catalog/releases及指定release下的search、definitions、lists、legacy/resolve。
- 本人管理：GET /api/characters/:id/management，POST /api/characters/:id/management-commands；DM状态走独立state-management入口。
- 建卡：POST /api/character-builds/preview、POST /api/characters；创建前结果用GET /api/character-builds/commands/:commandId核实。
- 成长业务：POST /api/characters/:id/operations/preview、POST /api/characters/:id/operation-commands。
- 历史导入：POST /api/character-imports/preview及commands；来源补选、DM资产批准分别有独立命令。
- 历史/结果/备份：授权history、commands及exports接口；查询本身不领取奖励或改资产。

完整方法、路径和错误见B1～B5契约。命令族可以共用账本和事务设施，但不同输入、权限和回执不混成一个任意写接口。

### 13.2 存储方案

建议关系元数据＋JSONB完整CharacterDocument，领域结构单一，常用权限和修订字段有关系约束。

| 记录 | 核心字段与约束 |
| --- | --- |
| CharacterPersistenceRecord | 主键、owner、revision、lifecycle、timeline、当前团关联、完整document、UTC系统时间 |
| CharacterSnapshot | 唯一(characterId, revision)，完整文档或可靠不可变引用，operationId、原因与时间 |
| CommandLedger | 唯一(verifiedPrincipalId, commandId)，family/target/payloadHash、可信输入、pending/终态、提交版本 |
| AuditRecord | 服务生成operationId、操作者、业务类型、目标、差异及依据 |
| Choice/Grant/Payment关联 | 正式选择、逻辑授予事件、支付和资产流水能追到同一operationId |
| Migration与Claim记录 | 来源版本、UID映射、声明修订、审批及物化防重键 |
| 团角色关联 | 同线单团约束；第一次绑定的timeline身份随后固定 |

表名为设计建议，实际SQL/Drizzle由双方约定。规则发布可先使用不可变数据包，不必为公开查询提前引入可编辑规则数据库。

### 13.3 同一业务提交一次完成

推荐分为短注册与执行事务：

1. 验证身份、命令结构及基本对象访问，按可信principal＋commandId注册pending，保存payloadHash；此步不产生角色或资产收益。
2. 执行事务锁定角色及受影响资产，重查当前权限、revision、规则包及资产版本。
3. 服务重新计算受控意图，检查费用、条件、选择、永久限制和接受的方案。
4. 原子写入当前角色、新快照、审计、支付/授予/资产流水、迁移批准和命令终态。
5. 提交后按当前权限生成回执；网络失败时可查询同一命令结果。

operationId由服务生成，是不同用户间的全局关联；客户端commandId不是全局可信操作ID。奖励还需实际成长/授予的逻辑防重键，不能仅靠commandId防重复领取。

### 13.4 超时、并发与恢复

- 同键同内容重放返回同一结果；同键异内容拒绝。
- 请求超时保留原冻结命令，查询原键；“暂未查到”不能直接认定从未提交。
- pending需租约、可恢复执行及崩溃后的处理，不允许永远悬挂。
- 未核实结果前不发依赖其收益的新命令。
- 回执展示提交时的快照，但按当前权限过滤；当前UI已有更高正式版本时不能倒退。
- 发生409保留基线和输入，三方比较；权限变化导致某字段不可写，也保留待审输入。
- 资产失败必须回滚同一业务中的角色变化；不让升级成功却扣费失败，或装备变更只完成一半。

### 13.5 历史与恢复

历史是不可变记录，恢复生成新revision，不覆盖旧快照。恢复只能作用于允许恢复的角色内容，永久禁学、已支付/领取、时间线、归属、钱包、库存及审批不得借恢复重置。

等级回退、撤销永久限制或经济纠错涉及额外规则与权限，不能作为通用“恢复整份JSON”隐式实现。数据库灾难恢复也要包含命令、资产、批准和授予流水，不能只恢复角色JSON，否则会重复发放。

## 14. 未来战斗引擎的接入边界

### 14.1 当前做什么，后续做什么

基础战斗调查已用于确定动作、资源、数值来源与角色结构，避免迁移后再拆模型。详细职业效果的执行、完整反应排序、地图、敌人AI和全技能自动化延后。

旧原型已有通用UnitInstance、种子随机数、距离和受限表达式等可参考内容；部分行为仍与职业和PveGame耦合。迁移时保留思路、样例和检查目标，复用代码前需审查适用规则。

建议未来模块消费DerivedActorSnapshot、版本化定义和受限机制片段，自己维护CombatEntityState、BattleState、EffectInstance及EventLog。战斗运行时不写入角色草稿；战后哪些资源需回写，要走明确有权限的角色操作。

### 14.2 已核对的基础约束

以下为模型必须容纳的当前结论摘要，不替代完整规则原文。

| 范围 | 当前规则摘要 | 引擎结构要求 |
| --- | --- | --- |
| 回合区间 | 玩家回合在所属区间开始；该区间所有玩家行动完毕时结束；敌人普通行动与玩家分开 | 公共玩家行动批次和个人边界，不能固定每人连续整回合 |
| 动作预算 | 默认1主要＋1附赠，区间再次开始恢复；允许放弃，无行动能力视为完成 | 每单位可修改预算及完成状态 |
| 多动作技能 | 1动作为主要，0动作为附赠；2/3动作连续支付主要动作，可跨回合，有额外主要可加快 | 持续施展进度，首付资源和次数、不退款；中途其他行动或下一回合不续付会中断，完成后再用附赠 |
| 反应 | 每场累计最多3次，可重复同种；不占第一行动；敌人可在玩家行动时反应 | 场次计数、触发窗口、独立能力次数 |
| 速攻/精锐 | 普通格挡赶不上速攻伤害前窗口；精锐按技能实际来源阶位阻止低阶反应且不扣费 | 精确来源Tier与窗口资格检查 |
| 第一行动 | 只能自身回合用的无动作效果也占；可回合外释放的效果不占 | 施展窗口独立于动作费用 |
| 阈值惩罚 | DM可裁定敌人无动作插入，不要求自动阈值系统 | 未来人工事件入口；不实现阈值调度 |
| 命中 | 武器：属性＋普通武器熟练（不累加、最高1）＋可叠额外熟练＋其他效果；法术：对应职业关键属性＋其他效果 | 来源明确的加值类别；法术不加武器熟练 |
| 暴击/大失败 | 按自然骰面，改到20/1不算；暴击率增量可叠，“19视作暴击”不与增量叠加 | 原始骰面与最终值分别记录 |
| 豁免/对抗 | 豁免最终值严格大于DC才成功；护甲检定只看D20且等于DC也成功；对抗平局重掷到胜负 | 检定类型及边界不能统一 |
| 优劣势/重掷 | 同类最多生效一次，先抵消同级；无法移除劣势不能消掉；普通/极大整组2/3骰重掷，伤害低骰按单颗重掷 | 骰组、来源、不可移除标志和重掷范围 |
| 伤害链 | 明确独立攻击段各算命中/抗性，其余按规则合并；抗性→护盾→护甲→临时生命→生命 | 分段、分层消耗及精确中间值 |
| 附伤与取整 | 结算后附伤不乘暴击，仍经过防御链；玩家造成向下、受到向上，按已确定阶段取整 | 暴击参与与防御参与分开；记录取整阶段 |
| 临时资源 | 临时生命、临时疲劳多来源取最高，原“叠加”答复已更正 | 来源池与叠加策略独立 |
| 限定护盾/护甲 | 生物限定护盾在适用时优先；护甲余额无小数，敌向上、玩家向下 | 适用条件、优先级及资源取整 |
| 时长/控制 | 通常一轮到施术者下次回合开始；控制按被控者边界，尚未轮到时计数有特殊锚点；一轮6秒、一分钟10轮 | 生效时间与计数起点分离，不统一按全局round减1 |
| 状态移除 | 无特别说明的致盲/麻痹一般一轮；移除一个异常是选一种且去所有层；冻结需实际火焰伤害；昏睡常用累计25刺激阈值 | 状态类型、层数、解除依据和DM覆盖 |
| 死亡 | HP保留负值；负HP再受伤不继续扣HP而加1死亡标记；HP≤−最大HP即死；稳定伤势固定生命标记 | HP与生存阶段、死亡裁决进度分开 |
| 死亡标记 | 普通回合裁决与短/长休完整裁决有不同上下文；自然20加2生命、1加2死亡；恢复1HP以上清生命标记，死亡标记战内保留 | 不用一个无上下文计数器；主持补充单列依据 |
| 移动 | 一次全速移2倍基础移动力，可穿插行动及其他玩家，余额到自身回合结束；墙角/敌占格不可穿，借步例外穿友格不落格 | 路径、预算、例外通行，不是一次性瞬移 |
| 借机/空间 | 离开敌相邻或周围移动超过3格可触发，同单位每回合1次，不耗动作或反应总额；斜邻示例2米仍相邻，圆环二维 | 借机资格和反应预算分离，区域声明维度 |
| 掩体/坠落 | 掩体角度DM裁定；瞄准到下次攻击，回合结束/遮视失效、移动不失效；坠落按(高度/2)D6，可经物理防御链 | 环境事实和裁决入口，不从示例推所有地形 |

具体尚未审完的例外仍留问题，不能将上表直接编译成完整引擎。短休/长休、伤势恢复、疲劳不足施展、控制计时等详细例子在T04记录中；角色侧先保存来源及当前状态。

### 14.3 已审职业结论如何保留

战士C01-a/b审过22项能力和斗争部分升级，目的在于验证通用机制表达，不代表战士119项全部完成。

代表结论包括：猛击的额外力量不乘暴击但先与普通伤害合并经过防御；12级后普通攻击基础一份力量之外额外两份。武器专精选一个类别；伤害优势取较高整组。连斩未被反应躲掉的每段即使未命中也支付2疲劳。致死打击比较当前HP与理论最大伤害，包含等于。18级愈战愈勇首轮锁1且抵抗处决；葬送复制剩余数值和时长并夺走原收益，原目标战后是否恢复由DM裁定。

这些结论以规则决定保留，不现在逐条制作执行器。冻结之触规范效果按法师，旋风挣脱DC统一12；召唤宝石兽差异仍待定。同名来源阶位依然分别保留，不因为统一效果而统一职业归属。

### 14.4 后续引擎审查方法

未来开始战斗开发时，以基础流程搭事件骨架，再按机制族审职业：动作/支付 → 检定/伤害 → 池/状态 → 触发/反应 → 移动/区域 → 召唤/控制。每类用真实技能和反例验证后扩展受控EffectSpec、TriggerSpec、DurationSpec等结构。

未知机制允许完整资料可读，但自动执行返回unsupported或needs-decision；DM裁决记录到事件，不悄悄猜规则。战斗结束回写、休息恢复和使用次数持久化须在对应功能前补结构与事务，现有手工状态并未实现这些自动化。

### 18.2 已有具体解法的设计缺口

| 缺口 | 具体解决方法 |
| --- | --- |
| CharacterRecord缺owner | 增加可信服务封装，导入不能自行指定 |
| 严格管理v1承载不全 | 保持原协议，增加版本化Workspace及状态DTO |
| 草稿没有正式Choice UID | 提交临时键和值，服务验证后分配记录 |
| 正文旧载荷与Schema不符 | 独立规范投影，保留注记；正式发布重新修订及哈希 |
| 普通数字编辑会覆盖来源 | 限定hp/fp等注册字段，池状态按UID意图更新 |
| 重复授予仅靠命令防重不够 | 增加建卡草稿、逻辑授予事件和迁移物化防重 |
| 角色版本没变但资产变了 | 提交AssetBasis，重查物品/容器/归属/版本 |
| 快照可能撤销永久事实 | 恢复走受控新操作，限制和流水保持，不整文档覆盖 |

### 18.3 仍未确定的规则及实施范围

- 遗忘/替换的额外费用、风格在删除或同批学习后的顺序、附赠职业和重复机制的容量贡献。
- 色彩标识消耗/替代细则；奇械师资料待更新，不能以旧彩色技能点推导新规则。
- 召唤宝石兽的成长及持续差异；其他同名但效果不同的来源应反馈，不自动合并。
- DM裁定的叙事条件、掩体、部分控制刺激与葬送战后收益，保留裁决事实。
- 各资料kind的完整可计算载荷、首个合法建卡组合的选择/物品/币种、随机分支支持范围。
- 正式身份、权限端口、物理事务边界、命令保留和恢复周期、草稿容量与期限、XLSX新版元数据。
- 团退出/转团/关闭、删除与归档、角色回退的具体政策；不默认允许跨线或清历史。
- 真机、真实团和真实旧档往返、全量自动规则，尚无正式验收结果。

未决机制不阻止完整资料展示；只有依赖它的自动操作才阻塞。必需功能未完成必须留在覆盖清单，不能临时改为“人工处理”并宣称一期完成。

## 附录A：核心结构示意

以下摘取领域候选中的主要关系，帮助理解章节；不是完整生产Schema。完整字段和运行时校验见材料索引，正式实现以共同评审后的同源结构为准。

~~~typescript
interface DefinitionRef {
  readonly id: string;
  readonly revision: number;
}

interface RuleReleaseRef {
  readonly id: string;
  readonly manifestHash: string;
}

type Recorded<T> =
  | { state: "known"; value: T; evidenceRefs: readonly string[] }
  | { state: "unrecorded" }
  | { state: "unresolved"; inputFactId: string; issueRefs: readonly string[] };

interface AbilityEntry {
  readonly ability: DefinitionRef;
  readonly sourceList: DefinitionRef;
  readonly sourceClass: DefinitionRef | null;
  readonly tier: Recorded<DefinitionRef>;
  readonly styles: readonly DefinitionRef[];
  readonly acquisitionRule: DefinitionRef;
  readonly sameNameGroup: string;
}
~~~

能力实例的核心关系：

~~~text
LearnedAbility.uid
 ├─ entry                 → 真实AbilityEntry
 ├─ acquisitionId         → 获取途径、选择、支付和操作
 ├─ placement             → 显示在哪个职业区或角色区
 ├─ growth                → 使用哪个职业进度和政策
 ├─ keyAttribute          → 使用哪个关键属性绑定
 ├─ slot                  → 免栏 / 指定池占栏 / 待定
 └─ styleParticipation    → 按规则参与 / 排除 / 待定
~~~

生产角色记录的服务封装方向：

~~~text
CharacterPersistenceRecord
  characterId              不可变主键
  ownerUserId              真实登录归属
  revision                 当前正式修订
  lifecycle                active / archived
  timelineId               未首绑时可空；首绑后固定
  campaignAssignmentId     当前唯一团关系
  createdAt / updatedAt    服务UTC时间
  document                 完整CharacterDocument
~~~

一次提交至少关联：

~~~text
verifiedPrincipalId + commandId → payloadHash、pending/终态
                    ↓ 服务operationId
       选择 / 支付 / 授予 / 角色新revision
                    ↓
       不可变快照 / 资产流水 / 审计 / 回执
~~~

结构Schema能检查字段和形状，不能单独证明引用存在、游戏合法、操作者有权或跨资产提交原子。四个层次均要有独立验证。
