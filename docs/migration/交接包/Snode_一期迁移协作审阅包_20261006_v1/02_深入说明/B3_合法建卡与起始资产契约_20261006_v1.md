## 最小合法建卡的范围与前提

首批目标是一个可完整验证的职业／种族／背景及其固定起始选择组合，先证明选择、计算、角色与资产可以共同提交，再扩展其他组合。具体组合在来源齐全时确定，不以T07的5个构造角色或B3的合成Schema样例代替合法建卡证据。

| 必须具备 | 来源和责任 | 未满足时 |
| --- | --- | --- |
| 创建可用的公开规则包 | 固定RuleReleaseRef，来源已核对、规则语义已确认，且此组合有实现覆盖；3.1负责 | 完整正文可读但未支持计算，返回unsupported或needs-decision，不生成角色 |
| 种族、背景、属性、选择、熟练和物品定义 | 补齐该组合所需payload及注册表；B1的55项metadata-only样例不足以支持其自动创建 | 引用存在不等于取得资格；不能从名称猜费用或起始收益 |
| 既有建卡规则 | F45确认继续现有规则；实际购点、修正、HP／FP和起始装备／货币从对应发布数据解析 | 不把战斗设计手册公式或合成例数值当作计算依据 |
| 真实身份与保存基础 | B2的verified主体、完整文档Schema、命令恢复、快照及权限 | 匿名本机演示不升级为云端合法角色 |
| 角色独立资产接口 | 3.2提供受同一事务控制的角色钱包／库存初始化、物品规范和币种单位 | 只生成角色再补资产，不能验收为B3闭环 |

第一条验证流程优先固定购点和固定起始资产分支。随机起始值、复杂叙事裁定或尚未确认的例外，须在其规则、一次性随机／批准事实及使用限制明确后纳入支持范围；预览刷新不能偷偷重骰。普通建卡不允许客户端指定高等级、当前经验、最终生命上限或任意已学技能。

## 提交输入与可接受的选择

| 输入 | 含义 | 服务验证 |
| --- | --- | --- |
| ruleset／profile | 精确发布引用；显示名称与故事，沿用v1文本／UTF-16预算 | 发布存在且允许创建；名称非空；身份及权限不来自profile |
| mainClass／keyAttribute／race／background | 具体定义引用，非人物程序class | 目标kind、职业关键属性选项及组合资格；进度与起始等级由规则生成 |
| allocationRule／baseAttributeTargets | 购点规则和未含种族／职业等修正的基础属性目标值 | 覆盖当前规则要求的八项属性、无重复／未知子项、费用及预算正确；不信任客户端汇总 |
| choices | ChoiceSubmission含clientChoiceKey、choiceDefinition及受控ChoiceValue | 职业、起始特性、种族、背景、熟练和装备选择属于当前建卡要求；数量、互斥、值域及必选项完整 |
| buildDraftId／submittedDraftVersion | 本机草稿身份及冻结输入版本 | 与当前请求／预览对应；不作为服务身份或正式角色ID |
| acceptedPreview | 用户已看过并接受的previewId与planHash | 当前主体／草稿／输入／规则一致且未过期，提交重做计划后Hash仍一致 |

首次创建没有现角色expectedRevision，也不接收characterId、ownerUserId、团／时间线声明、最终CharacterDocument或资产余额。新的选择都来自本次提交，不能引用另一个角色的choiceRecordId；服务生成正式ChoiceRecord及UID后才交给领域解析。

起始能力与特性、图纸、知识、机制及槽位收益按实际持有类型保存。免费与占栏独立，初始一阶及风格按确认来源处理；预览必须显示来源和获取途径，不把所有奖励塞入普通技能数组。切换职业或种族重新校验下游选择，失效项保留本机待处理但不进入正式创建。

## 预览接受与计划一致性

预览请求关联requestId、buildDraftId、submittedDraftVersion和输入指纹。ready只在所有必需选择、派生值、规则及资产计划可确定时出现；needs-selection、needs-decision、unsupported都有可定位原因，不签发可创建的接受信息。

语义planHash包含发布、创建／资产政策版本、选择／费用／角色收益和起始资产分配，不包含尚未生成的随机UUID、预览时间或会变化的显示包装。服务重做同一语义计划仍应相同；用户改变选择、规则／政策变化或资产规范变化后要求重新预览，不能带着旧确认悄悄创建另一结果。

previewId仅关联短期计算结果，不授予权限、不证明合法资产、也不是跨设备云草稿。提交仍要验证身份、输入及当前政策。预览不扣点、不创建正式角色、钱包或库存；需要随机／叙事事实时使用另行确认的受控记录，缺记录不采用客户端自报结果。

## 起始资产计划与账户边界

| 计划字段 | 责任与含义 | 一致性要求 |
| --- | --- | --- |
| recipient=new-character | 接收者是此次服务创建的新角色；钱包／库存以characterId拥有，账户只承担访问权限 | 不允许把起始物资指向旧角色、玩家共享钱包或别人的容器 |
| currencyAllocations | 币种、初始分配、创建预算内消费、净余额、来源依据 | 净额＝分配－消费且非负；币种单位／比例由3.2注册，不硬编码兑换率或当前市场价 |
| itemGrants | 稳定grantKey、精确物品定义、数量、起始授予或创建预算购买来源 | 来源和数量由规则重算；唯一个体与可堆叠数量按统一物品规范实例化 |
| placement | 携带、配装槽位，或同次创建的parentGrantKey容器 | 容器存在、没有环、容量与槽位条件合法；不借用其他角色的库存 |
| assetPolicyRevision | 物品／币种／价格及初始化规范的版本 | 与用户接受的计划绑定，变化先重新预览 |
| unassignedTransferPolicy | 用户确认hold-and-equip-only | 未入团仅持有、查看和配装／卸下；市场买卖和跨角色转移不开放 |

如果起始装备需要花起始资金，计划明确分配和内部消费，流水一起记录；不从另一角色钱包补差，也不默认走市场交易。金额使用注册币种的最小单位安全整数传输，单位、取整及价格来源需3.2与3.1核对，不能把软件安全整数界限当游戏财富上限。

入团不会自动转移起始资产或改ownerCharacterId，交易资格是当时的服务权限。配装也须检查本角色所有权和当前限制；当前金币／库存后续从资产权威读取，不以创建回执的历史金额作为最新余额。

## 原子创建与两层防重

| 阶段 | 同一操作应完成的处理 |
| --- | --- |
| CREATE_TX01 验证与登记 | 验证主体、输入、已发布规则、预览关联和创建资格；登记principal＋commandId、指纹、operationId、pending |
| CREATE_TX02 草稿唯一归并 | 在执行事务锁定principal＋buildDraftId的物化记录；已物化同键复用，异键返回already-created，不重发物资 |
| CREATE_TX03 重做计划 | 按当前绑定发布和创建／资产政策，复核八属性、选择、预算、来源、栏位及起始资产；重新比较acceptedPlanHash |
| CREATE_TX04 分配正式身份 | 服务生成characterId、进度／选择／获取／能力UID、itemInstanceId和walletId，建立临时键映射；owner来自登录，团／时间线为空 |
| CREATE_TX05 原子写入 | 完整角色revision1、创建／授予记录、钱包及流水、库存及配装／容器、初始快照、审计、草稿物化映射及命令committed一起提交 |
| CREATE_TX06 响应与恢复 | 回执从已提交结果按当前权限渲染；发送失败查询原创建命令，pending租约恢复；事务故障全部回滚 |

沿用B2的命令登记短事务与执行事务：pending只登记受控请求，不产生可见角色或资产。执行事务中的角色、钱包／库存、配装、授予、初始快照、审计、草稿物化关系和committed命令结果必须一起成功或一起回滚。

服务端内部资产接口建议为createInitialAssets(transaction, operationId, newCharacterId, trustedAssetPlan)。它由服务持有事务与真实接收者，客户端不调用内部“授予”函数。3.2若另用独立数据库或无法参与共同事务，需要另定可恢复初始化与对账协议；未解决前不把“角色已存、资产稍后补”报告为B3完成。

| 防重键 | 处理方式 | 用户结果 |
| --- | --- | --- |
| verifiedPrincipalId＋commandId | 同请求重试查询／重放同一终态，异payload拒绝 | 只一份角色与起始资产；不换键试图解决未知结果 |
| verifiedPrincipalId＋buildDraftId | 同草稿最多物化一次；另一个新commandId碰到已物化记录，返回build-already-created而不发奖励 | 提示打开此前创建角色；不能把旧命令回执伪装成新命令回执 |
| operationId＋grantKey及角色初始化关联 | 同操作钱包／物资／授予分项有可信来源和防重复关联 | 事务重试与恢复不能单独再次发钱或装备 |
| 显式新角色草稿 | 确实要另建人物时使用新buildDraftId，重新完整预览及校验 | 不把复制旧云角色／历史导入混作合法首次建卡 |

同草稿两次提交应在并发事务中争用同一物化约束，失败的一方不能留下第二个角色或部分库存。账户切换后草稿作用域重新核对，不因本机contextKey相同就继承另一账户身份。

## 创建回执与失效恢复

首次成功角色修订为1，CreateReceipt属于独立合同，包含原commandId／draftVersion／buildDraftId、服务operationId与characterId、ManagementView、选择／能力／资产grantKey到正式ID的映射，以及initialization-at-creation资产证明。它不扩展既有三字段CommitReceipt，建卡编辑器也不使用一个共用“new”角色ID。

回执内角色、操作和资产ownerCharacterId必须一致；配装／容器与正式物品实例的映射一起建立。客户端采纳匹配冻结命令的结果后进入该角色工作区，已继续修改的输入仍是新草稿。重新读取当前角色和资产时使用当前服务修订，旧初始化回执只作历史证明，不能重新发物资或覆盖已交易后的资产。

| 情况 | 建议处理 |
| --- | --- |
| 选择未完成、预算不足或规则未支持 | 422或相应预览阻塞结果；保留输入并定位，不创建半个角色 |
| 输入或语义计划已变、预览过期 | 409 preview-stale；重做预览并让用户重新接受，不自动创建新价格／收益结果 |
| 同草稿已创建、使用新命令键 | 409 build-already-created；当前主体有权限时返回此前角色定位，不重复授予 |
| 同键异请求 | 409 idempotency-key-reused；原命令不变，修正意图另建命令但仍受草稿物化约束 |
| 提交响应丢失或not-seen | 查询创建命令核实；not-seen不是未提交证明，按一致性／租约等候或重发同键 |
| 钱包、物品或配装写入失败 | 执行事务回滚；pending可核实恢复，无正式半成品 |
| 权限撤销或已创建角色访问范围改变 | 重新按当前范围检查核实／回执，不盲返回旧缓存的完整私有结果 |

## 创建前无角色ID的接口

| 候选接口 | 用途 |
| --- | --- |
| POST /api/character-builds/preview | 以当前登录主体、buildDraftId和受控BuildInput做服务预览；不创建角色／发资产 |
| POST /api/characters | CreateCharacterCommand，服务器重做规则及资产计划后原子创建 |
| GET /api/character-builds/commands/:commandId | 创建前无需characterId的命令核实；仅当前发起主体并按结果对象权限访问 |
| GET /api/character-builds/:buildDraftId/materialization | 核对该主体草稿是否已生成角色；恢复页面和同草稿新键碰撞处理 |

B2的角色命令核实路径需要characterId，不能用于尚未创建角色的超时恢复；因此本合同新增主体范围的创建命令／草稿物化核实入口。创建服务仍按B2的可信身份、幂等保留、pending租约、当前授权和安全错误规则处理，角色ID出现后再接普通管理端口。

## 本轮验证与共同评审门槛

[Schema候选](../01_计划与设计材料/B3_建卡与起始资产Schema_评审候选_20261006_v1.json)复用B1／B2的角色和选择基础，新增18个定义、6项顶层合同。[合成样例](../01_计划与设计材料/B3_契约验证样例_20261006_v1.json)有24项结构例，7项通过、17项拒绝，全部匹配预期；另外7项结构可过的局部计划反例被识别，覆盖预算净额、grant重复、缺容器／环、槽位冲突、ready仍有未知值及回执身份不一致。
