## 目录载荷与正文关联的规范投影

更严格的Schema核对发现，T07目录样例中有38项记录不能按假定载荷直接通过：30项content使用contentDocumentId链接正文，6项class和2项domain含sampleCoverage／synthetic等评审标记。5份角色和30份正文结构本身通过检查；这些差异不是已验证的游戏规则出错。

[规范目录投影样例](../01_计划与设计材料/B1_规范目录投影_评审样例_20261006_v1.json)采用明确转换：content载荷保存document的id＋revision，正文放在独立PublishedContentDocument；8项评审标记保留在reviewAnnotations侧表，不混入正式职业／领域载荷。原T07文件不改，其他未知字段不按白名单之外的规则静默删除。

| 类别 | 第一批处理 | 不混淆的范围 |
| --- | --- | --- |
| class、ability-entry、ability、domain、tier、entity-template | 采用对应闭合payload Schema，投影保留来源与引用 | 结构可验证不表示规则计算已支持 |
| content | 储存版本化正文引用，详情解析实际ContentDocument | 不能把正文链接当作整篇正文，也不复制一份脱离版本的摘要 |
| 其他kind的55项样例记录 | 先提供定义摘要和完整可核对正文；API payload标text-only，并禁止附带任意value | 尚未定义载荷结构不能冒充typed；所需计算Schema在对应功能前补齐 |
| 评审／合成来源 | sampleOnly与publicationAllowed=false贯穿本轮投影和验证样例 | 不能把构造角色、合成职业或评审样例发布为现行规则 |

规范投影仅为评审对照而保留原样例引用，不能直接复用旧manifestHash当正式发布结果。实际已发布资料转换必须产生新修订与新发布包，重新建立引用及Hash，旧角色仍读取原版本。

## 保存事务与命令恢复

| 阶段 | 具体处理 | 失败与重试 |
| --- | --- | --- |
| TX01 接收与认证 | 验证真实主体、对象范围、路径／正文ID一致、命令结构、字段登记及预算 | 未授权不泄露角色；结构错误没有角色写入 |
| TX02 命令登记短事务 | 以verifiedPrincipalId＋commandId唯一登记family、目标、指纹、完整受控请求、operationId和pending状态 | 同键同请求复用；异请求拒绝；凭据不进入请求记录 |
| TX03 执行事务读取 | 锁定命令和当前角色／关系依据；重新核验当前权限、lifecycle及expectedRevision | 落后基线返回高版本conflict；未来基线明确拒绝 |
| TX04 应用与校验 | 只应用登记意图，建立由operationId标识的事实；完整文档结构及受影响关系／值域重新校验 | 确定不合法记录rejected；原角色／资产不变 |
| TX05 成功原子提交 | 角色revision＋1、完整文档、不可变快照、审计及ledger committed结果同事务写入 | 事务故障全部回滚；短事务pending保留，租约到期后核实并重试原命令 |
| TX06 回执及重放 | 按当前读取权限从已提交快照渲染匹配回执；核实原commandId；已有更高客户端基线不倒退 | 发送失败不等于提交失败；不盲回存储的旧完整响应 |

命令全局关联需要两个ID：commandId是客户端幂等与回执键，唯一约束是verifiedPrincipalId＋commandId；服务另生成全局operationId用于事实、快照及审计关联，避免不同主体碰巧使用同一commandId混淆来源。指纹包括合同族、目标、expectedRevision、submittedDraftVersion和完整登记意图；只做确定性序列化，不改写文本含义。

登记pending的短事务不修改角色。执行事务更新角色、快照、审计与terminal命令结果。请求并发时由唯一约束／锁保证同键只应用一次；pending有执行租约及恢复流程，服务重启后重新核实并处理原请求，不能永久卡住或直接换键重做。成功关联记录按角色／快照保留，不仅放在有短TTL的缓存里。

已提交命令先查幂等结果，再检查它是否是新的写入；不能因当前revision增加把同一已完成命令报成新冲突。重复读取结果仍须当前授权，从committedRevision对应快照渲染匹配回执，不盲返回存储的旧完整响应。权限失效拒绝读取私有结果；pending／not-seen都不证明此前一定未提交。

确定拒绝或冲突可以保存命令terminal结果，但不改角色和资源，不生成成功快照。基础设施故障回滚执行事务，pending仍可按租约核实并恢复。提交响应丢失时客户端保存冻结命令及在途检查点，用同键查询或重发；新的输入留作本机草稿，暂不提交依赖未知结果的新命令。

## 与现有管理v1的具体兼容规则

实际editor.ts要求成功回执的characterRevision严格大于expectedRevision，冲突视图也必须高于提交基线。因此采用以下建议，避免后台看似成功而界面拒绝回执。

| 情况 | 服务响应建议 | 现有编辑核心衔接 |
| --- | --- | --- |
| 客户端检测没有改动 | 不发送空edits请求，保留unchanged行为 | 无需生成命令和修订 |
| 服务接受非空、授权且合法的新管理命令 | 包括同值复写，成功产生新revision及审计／快照；重试同键不再增版 | 三字段回执view.revision＞expectedRevision，符合completeSave |
| expectedRevision低于服务当前修订 | 409 conflict，返回当前授权高版本投影 | 交给acceptConflict，保留原输入及基线 |
| expectedRevision高于当前修订 | 明确422 invalid-base-revision，不伪装普通conflict | 按拒绝处理保留输入，重新核对来源／会话；不送进要求更高版本的acceptConflict |
| 字段越权或未登记、资料非法 | 403或422明确拒绝，返回安全可定位错误 | 不当成未知网络结果；输入仍可修正 |
| 同键不同请求 | 409 idempotency-key-reused，原请求不变 | 新意图应新键；不能偷偷修改已冻结请求 |
| 已知成功回执与已有更高本机基线 | 确认原命令结果，界面不回退到旧修订；按条件刷新 | 不同会话／旧操作回执不覆盖当前编辑 |

普通管理字段第一批为名称、故事、hp.current和fp.current；服务把数值set映射为Recorded.known人工事实，clear映射unrecorded，更新由operationId记录。它不执行战斗伤害、豁免或死亡裁决。临时生命、护盾、力竭依旧通过来源池／状态UID的后续命令处理；XP、技能点、等级、钱包及库存不成为任意set-number字段。

管理v1命令及CommitReceipt本身保持严格字段不变，评估、UID映射和新操作放新包装DTO或独立合同。B2历史只读取和核对，不提供整份快照直接覆盖当前角色的写入口；后续恢复产生新修订，并重新检查规则及资产。
