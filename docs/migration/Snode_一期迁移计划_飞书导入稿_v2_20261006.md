**图文审阅版 v2 · 2026-10-06 · 建议阅读约10～15分钟**

这份方案用于讨论：旧项目的哪些成果能继续使用，哪些部分需要重做，以及怎样接入新的Snode项目。

**建议保留规则正文、已核对的规则和有效工具；统一资料与角色数据；沿用新项目已有的角色编辑机制，逐步接入云端和资产服务。** 第一批先完成“搜索资料→查看完整详情”，随后完成一个角色的创建、保存和成长。

当前总体设计已形成，目标项目也有角色编辑和草稿的本地候选；正式资料库、完整云端角色及资产业务仍待实现。字段定义、接口草案、规则答复和验证记录放在详细技术参考（技术附件），评审总体方向时可以先读本正文。

## 1. 迁移要解决什么

旧项目已有较多规则内容和角色工具。迁移的重点，是让这些内容在新项目里使用同一套数据和清晰的业务边界。

| 当前问题 | 新项目需要达到的结果 |
| --- | --- |
| 上传、搜索、学习面板与技能树的数据不一致 | 所有入口读取同一版本的资料，更新一次即可共同使用 |
| 跨职业技能导入后丢失来源、阶位或成长依据 | 保留玩家实际怎样获得技能，以及它应按什么规则成长 |
| 技能详情遗漏召唤物、固有动作或表格 | 资料库、学习面板和已学技能均能查看完整内容 |

一期范围对应开发文档的三个部分：**3.1.1资料库、3.1.2建卡与计算、3.1.3角色管理与导入导出**。登录、团、云端存储和钱包库存与3.2协作接入。

完整战斗引擎后续建设。本次把它需要的角色、技能和单位数据准备好，详细战斗效果可以在开发战斗功能时再审查。

## 2. 哪些复用，哪些重做

“复用”分为保留内容、适配已有实现；不能只因为旧页面能运行，就直接把其全部逻辑搬入新项目。

| 功能部分 | 可以继续使用 | 需要重做或接入 |
| --- | --- | --- |
| 规则与世界观 | 职业、种族、背景、领域、物资原文，以及图表和已核对解释 | 统一编号、版本、来源和关联；旧公式逐项核对 |
| 资料查询 | 分类习惯、别名搜索和有效展示方式 | 同一资料库、统一全文组件、完整召唤物详情 |
| 角色创建 | 建卡步骤、合法选择和确认过的计算规则 | 按定义生成选择、统一预览、正式创建与起始资产 |
| 角色面板 | 新项目已有的编辑、草稿、冲突处理和恢复机制 | 完整角色数据适配、真实账号、云端历史 |
| 升级与学习 | 已确认的成长、栏位、前置和获取规则 | 有来源的获取记录、费用检查、永久限制与一次性授予 |
| JSON与Excel | 原始值保留、实例编号和元数据的有效处理思路 | 多表多角色选择、来源补选、云端权限和真实往返 |
| 装备与库存 | 物品定义、装备分类、起始装备和图纸内容 | 角色独立资产、权威库存、配装及相关事务 |
| 战斗与其他扩展 | 规则调查、单位模板和经过审查的原型思路 | 后续战斗执行；AI顾问、卡牌等另定交付范围 |

技术实现沿用目标项目的React/TypeScript、Fastify和PostgreSQL。具体旧算法能否直接适配，应在实施该功能时核对；旧战斗设计手册中的计算公式不作为可信实现依据。

## 3. 总体怎样接入新项目

![图1](@./assets/迁移总体计划_v2/01_总体接入.png)

**图1：各页面共用资料和业务入口。虚线部分为后续战斗。**

这里有三个关键边界：

- **资料中心**保存共用的职业、技能、物品、规则正文和单位模板，并使用固定发布版本。
- **角色记录**保存某个人物的选择、成长、已获得能力和当前状态；正式保存后进入云端并留历史。
- **资产服务**持有真实钱包和库存。角色记录引用装备，不能用上传文件或旧快照直接覆盖余额。

浏览、建卡和面板复用同一份规则解释与计算。服务器提交时再次校验身份、条件、费用及当前版本，相关变化一起保存。

代码可按领域数据、资料读取、规则计算、页面和服务提交分职责。是否立即拆成独立包，由两位开发者共同确定；这不影响上述边界。

## 4. 数据怎样抽象，才能继续扩展

![图2](@./assets/迁移总体计划_v2/02_角色与能力.png)

**图2：新增人物增加一份记录；职业、技能和领域通过共用定义扩展。**

一个新的角色不需要一个新的程序class。角色使用通用结构，职业、阶位和领域是它引用的资料与选择。

| 数据 | 主要保存什么 | 作用 |
| --- | --- | --- |
| 共用资料 | 稳定编号、版本、完整正文、来源；职业成长、技能表、领域、物品与单位关联 | 多个角色和页面可以共用 |
| 角色职业进度 | 主/子职业、等级、关键属性、进阶和已开阶位 | 职业进阶保留原进度，不重建人物类型 |
| 已获得能力 | 实例编号、真实来源条目、获取途径、成长依据、关键属性、栏位 | 同名技能和跨职业获取不会串来源 |
| 选择与成长记录 | 玩家选择、获得时的规则、实际收益和已领取事件 | 改属性或恢复历史不重新发收益 |
| 资源与状态 | 当前生命/疲劳、来源池余额、状态及依据 | 保留消耗结果，不在读档时重生成满额 |
| 服务记录与资产 | 角色拥有者、修订、团关系；钱包及物品实例 | 权限和所有权由服务判断 |

**跨职业技能是这次设计的检验重点。** 两个职业中同名技能可以共享效果正文，但仍有各自的来源和阶位。玩家通过专长获取后，还需按该获取规则确定成长、关键属性与占栏，不能仅凭技能名或它显示在哪一栏推断。

新增技能、职业、阶位或神圣领域，在已有机制范围内主要通过数据扩展；真正的新机制仍可能需要新的处理逻辑和验证。

缺少记录、已知数值0、来源尚未确认分别表示。历史资料不完整时保留原值和问题，不自动补成0或默认职业。

## 5. 各功能怎么落地

### 资料库：同一份完整内容，供所有入口读取

先把正文、图片、表格和召唤物资料整理成统一定义，再生成搜索索引。资料详情、学习面板、技能树和已学能力详情共用一个正文组件。

召唤物作为独立单位模板，关联全部固有技能和变体。详情要能继续查看这些内容，不能只显示召唤物名字或属性摘要。

已发布资料可未登录浏览和搜索。某段效果尚未支持自动计算时，仍可完整阅读，并明确自动化范围。

### 建卡与成长：保存选择和依据

保留职业、起始特性、种族、属性、熟练、背景、装备、确认的建卡步骤。选项由资料定义提供；前后端按同一规则版本计算。

先完成一个真实合法组合，再覆盖牧师领域、跨职业获取、召唤契约、图纸等分支。新建角色的必需选择未完成时留为草稿；合法角色可以先正式保存，再加入团。

免费获得的能力也可能占栏。满栏时需要用户决定，涉及遗忘或拒绝授予的永久禁学要明示；这些限制不能通过恢复旧档绕过。升级、起始收益和授予事件都要有防重记录。

### 面板与保存：复用已有编辑核心

![图3](@./assets/迁移总体计划_v2/03_保存与导入.png)

**图3：正式记录和本机草稿分开，导入和资产核对也有各自步骤。**

未保存输入先保留在本机；点击正式保存后上传云端并新增历史。保存过程中的新输入仍是草稿，发生版本冲突时保留输入供处理。

原有编辑、恢复和冲突机制继续复用，但要接入完整角色文档。面板用于显示的简化数据不能充当完整存档。

普通编辑与升级、学习、配装等业务操作分开。涉及角色、费用或资产的同一次操作应一起成功或一起回滚；网络重试不能重复扣费或发放收益。

### 导入与资产：先保留事实，再核对

导入先选择文件里的角色、工作表或槽位，再预览差异。技能和天赋的实例编号要保住；无编号的旧档建立稳定映射，同名记录不直接合并。

技能来源不明时，允许保存为待核对角色，保留原文、数值和实例编号；只限制依赖未决事实的操作。随后补选来源是在修正记录，不重新学习或重新发奖励。

每个角色拥有独立钱包和库存。旧档金币、物品先作为待核对声明，入团后由DM批准入账；不能直接覆盖云端资产。未入团角色可以持有和配装，市场交易及跨角色转移等入团后开放。

同一角色一期不跨时间线复用，同一时间线只加入一个团；首次绑定后不能靠清空团关系换时间线。转团、退出等具体流程与3.2共同确定。

新版JSON与约定Excel格式需验证真实导出再导入，覆盖多表、负数、公式缓存、同名和跨职业技能；第三方编辑造成的信息损失应明确说明。

## 6. 怎样与合作开发者分工

| 工作 | 3.1迁移功能侧 | 3.2服务基础侧 |
| --- | --- | --- |
| 资料与计算 | 资料整理、全文展示、条件和计算 | 协作确定共用编号、版本与接口 |
| 创建与角色操作 | 页面、输入、预览和变更计划 | 身份、权限、持久化与提交基础 |
| 面板与历史 | 完整角色适配、编辑、草稿和冲突展示 | 修订检查、历史、命令结果和恢复支持 |
| 装备与导入资产 | 配装入口、旧档声明和核对流程 | 钱包库存、当前归属、批准与流水 |
| 团与DM | 允许的操作入口和提示 | 单团/时间线约束、对象和字段权限 |

共享结构、API和数据库变化共同评审。每个业务操作只有一个提交入口，避免角色和资产各保存一半。

需要读取和修改的字段按权限返回；前端“可编辑”按钮和上传文件中的拥有者信息不能代替服务授权。DM管理状态也不自动获得角色全部私有故事。

## 7. 按什么顺序实施

![图4](@./assets/迁移总体计划_v2/04_实施路线.png)

**图4：先交付能体验的流程，再扩展资料和分支。**

| 阶段 | 交付结果 | 完成时必须证明 |
| --- | --- | --- |
| 1 公开资料 | 搜索到真实技能，查看全文与关联单位 | 各入口一致、关联完整、版本准确 |
| 2 云端角色 | 正式保存、重开读取、历史与本机草稿 | 真实登录和数据库、权限、冲突与失败恢复 |
| 3 合法建卡 | 一个组合从选择到角色和起始资产落库 | 合法计算、选择完整、收益只领取一次 |
| 4 成长与装备 | 升级、学习、放弃、状态及配装 | 来源/栏位/限制正确，费用与资产一致 |
| 5 全量与旧档 | 约定资料及建卡分支覆盖，真实档案往返 | 有全量去向清单，未知信息与实例编号不丢 |
| 6 协作验收 | 团、DM、经济、手机与真实试用 | 真服务证据；iPhone Safari核心流程可用 |

资料功能可以先推进，云端角色的共享约定同时准备。首次带资产的建卡或配装就要接入共同事务，不推迟到最终联调。

首批建议选能验证结构的一组内容：普通技能、同名不同来源、领域或跨表技能、一个召唤单位及其全部固有能力。验证真实来源和实际页面后，再增加覆盖；少量样例不能代表一期全部完成。

## 8. 本次评审聚焦哪些决定

建议先讨论以下三项：

1. **职责和数据边界：** 资料、角色、身份团关系、钱包库存是否按图划分。
2. **复用策略：** 是否沿用现有角色编辑核心，并用统一资料和完整角色结构适配。
3. **首批交付：** 是否先完成公开资料闭环，同时准备云端角色接入。

进入具体批次前，再确认其所需的字段、接口、权限和事务。奇械师待更新规则、未决费用及特定技能差异继续留在问题清单，不阻塞完整资料展示，也不擅自替它们补规则。
