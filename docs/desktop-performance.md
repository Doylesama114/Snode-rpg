# 桌面端性能诊断与优化计划

> 诊断时间：2026-09-20（第二轮补充：搜索/切换职业页 → 卡顿 → 白屏）
> 被测版本：**v1.0.7278**（用户实际运行构建）｜运行时：Electron **22.3.27**（Chromium **108.0.5359.215**）
> 全部数据来自真实 Electron 进程（CDP 驱动真实窗口 + 进程级内存采样），非估算。
> 本文件只做诊断与计划，**尚未改动任何代码**。

## 一、用户反馈现象的复现（第二轮核心）

**复现路径**（模拟用户操作）：`职业页/首页 → 点搜索结果进入某职业页 → 返回首页 → 再查再进另一个职业页`，循环 12 轮；每轮进入职业页后再做一次站内搜索。

**实测结果（渲染进程指标，页面「看起来」没变化）**

| 轮次 | 打开页面 | 活跃 DOM | 渲染进程累计节点 | 监听器 | 存活文档 |
| --- | --- | --- | --- | --- | --- |
| 1 | 法师 | 27,051 | 65,186 | 5,067 | 2 |
| 3 | 牧师 | 22,000 | 138,459 | 7,549 | 4 |
| 5 | 魔契师 | 9,140 | 169,824 | 1,809 | 6 |
| 8 | 牧师 | 22,000 | 312,882 | 7,550 | 9 |
| 10 | 魔契师 | 9,140 | **356,240** | 11,125 | 11 |
| 12 | 通用天赋树 | 18,786 | 320,486 | 8,212 | 9 |

**同一时刻的进程内存**：342 MB（启动）→ 607 MB → 815 MB → **1,017 MB**（渲染进程单独 725 MB）→ 渲染进程死亡后 296 MB。

**结论**：活跃 DOM 始终只有 9k~27k，但渲染进程里堆积了 **35 万个残留节点**、11 个未销毁文档。用户看到的"内存占用极大"就是这个；"卡顿"是期间 GC/布局在数百 MB 锯齿上反复抖动。

## 一之二、首页「搜索 → 点击结果跳转」耗时拆解（第三轮补充）

**真实路径**：`职业页/首页.html` 内搜索 → 点击结果行 → 跳转 `职业页/法师.html#m-skill-1-3-1`（跨文档整页导航）。

| 阶段 | 实测 | 说明 |
| --- | --- | --- |
| 首页本身加载 | 46 ms | 索引未加载时很快 |
| 搜索渲染结果行 | ~24 ms/次（防抖 200 ms） | 非瓶颈 |
| **点击 → load 事件** | **1,855 ms** | 整页加载 1.7 MB HTML + 27,051 DOM |
| **主线程累计阻塞** | **2,259 ms**（4 个长任务，最长 **1,050 ms**） | 用户感受的"卡住" |
| 其中 hash 定位额外开销 | 加载 +417 ms；最长长任务 660 → 1,050 ms | 见下 |
| 平滑滚动实际耗时 | **151~338 ms** | 跨越 scrollY 0 → **16,775 px** |
| 高亮动画 | 2.6 s 后移除 `skill-hash-focus` | 期间持续样式重算 |

**hash 定位为什么额外贵**（[职业页/common.js](职业页/common.js#L63) `focusSkillFromHash`）：
1. 先向上遍历父节点把祖先 `<details>` 全部 `open = true`（法师页共 60 个 `<details>`）→ 展开大子树触发全页重排；
2. 然后 `requestAnimationFrame` **和** `setTimeout(120ms)` **各做一次** `scrollTo({behavior:'smooth'})` → 两次跨 1.6 万像素的平滑滚动排队；
3. 再给目标卡加 2.6 s 的高亮动画类。

**另注**：同一页面内只用 hash 跳转（不换文档）不会重新加载页面，代价仅 ~150~340 ms 滚动；卡顿只发生在**跨文档**跳转（即从首页进职业页）——这正是用户反馈的场景。

**结论**：这条路径的耗时 = **整页加载巨型 DOM（约 1.4~1.9 s，主因）** + **hash 定位与平滑滚动（约 0.4 s，次因）**。前者归 P0-1（懒渲染），后者可独立低成本修掉。

## 二、白屏的确切成因（已验证）

用 CDP 强制渲染进程崩溃后实测：

- `Inspector.targetCrashed` 事件触发；
- 调试目标列表 **count = 0**（窗口里已经没有任何页面）；
- 进程数 5 → 4（渲染进程消失），内存掉回 293 MB。

→ **白屏 = 渲染进程崩溃/被 OOM 杀掉，而主进程既不重载也不提示**。
经查 [electron-app/main.js](electron-app/main.js) **完全没有崩溃处理**：没有 `render-process-gone`、`child-process-gone`、`unresponsive`、`did-fail-load` 任何一个监听器。用户唯一出路是手动关掉软件重开。

## 三、根因（第二轮新增，按证据强度排序）

### 根因 1：巨型 DOM + 高频整页导航 → 垃圾长期不回收（不是真泄漏，是"不回收"）

A/B 对照实验（同一操作序列）：

| 条件 | 起始节点 | 第 5 轮 | 第 8 轮 | **强制 GC 后** | 存活文档（GC 后） |
| --- | --- | --- | --- | --- | --- |
| 默认 | 62,392 | 231,116 | 188,046 | **42,511** | **1** |
| `--disable-features=BackForwardCache` | 62,392 | 274,464 | 196,120 | 42,511 | 1 |

两条曲线几乎一致 → **排除 bfcache**。而强制 GC 后节点从 18.8 万掉到 4.3 万、文档从 4 掉到 1 → **这些都是可回收垃圾，只是长期没被回收**。

原因链：
1. 职业页动辄 2~2.7 万 DOM（法师 423 张技能卡，每张卡 detail 全展开）；
2. 每次整页导航都新建一份这样的 DOM，旧文档变成游离垃圾；
3. 但 **JS 堆始终只有 3~6 MB** → V8 感受不到内存压力 → 不触发 GC → 依赖 V8 触发的 Blink GC 也不跑；
4. 于是 RSS 一路涨到 1 GB，直到渲染进程被系统/Chromium 干掉 → **白屏**。

### 根因 2：职业页站内搜索**没有防抖**，每次按键全量重排/重高亮

[职业页/filter.js](职业页/filter.js#L95) 绑定的是 `input` → 直接 `applySearch()`，无 debounce。`applySearch()` 每次要做：1 次全文高亮清除（`replaceChild` + `parent.normalize()`）、423 张卡的 `textContent` 序列化 + 归一化、**9 遍全文档 `querySelectorAll` 扫描**、再对每张可见卡 × 每个关键词做一次 TreeWalker 高亮。

实测单次同步耗时：**平均 24 ms，最大 45.8 ms**（48 次搜索累计 1.2 s 阻塞主线程）。中文输入法一次输入会连发多个 `input` 事件 → 连续阻塞，配合大页面即"打字都卡"。

### 根因 3：导航即整页重载 —— 首页每次都要解析 3.82 MB 索引

"查完一个职业 → 回首页 → 再查另一个职业"是最典型的用户路径，而：
- `职业页/首页.html` 每次打开都加载 `search-index.js`（**3.82 MB**，file:// 下 `fetch` 被 CORS 拦，降级为 script 解析）；
- 目标职业页 0.3~1.7 MB、9k~27k DOM；
- 加之每次导航主进程还要重新注入 3 个脚本（bug-report 10 KB + advisor-tips 6 KB + advisor-widget 46 KB）。

**一次"查一个职业"= 3.8 MB 索引解析 + 上万个新 DOM + 上一份文档变垃圾**，这正是根因 1 的燃料。

### 根因 4：无内存压力兜底、无崩溃恢复

- 主进程没有对渲染进程内存/崩溃做任何观测与处理（见第二节）；
- 没有被杀后的自动重载与用户提示。

### 根因 5（第一轮已结论，仍然成立）

- 空载即数百 MB（307~448 MB），其中相当部分是 Electron 22 / Chromium 108 的运行时基线；
- `autoUpdater.autoDownload = true` + 启动 3 秒即检查 → 后台下载 100.6 MB 安装包 → 下载完 3 秒自动静默重启；
- 创建页内嵌 iframe 预览职业页一次 +6 万节点、关闭不释放；「↗ 新标签页打开」每个新窗口一个独立渲染进程；日常操作峰值 **705 MB**。

## 四、修复计划（按收益/风险排序，先不改代码）

### P0 —— 直接对症，建议优先

| # | 改动 | 预期收益 | 风险 |
| --- | --- | --- | --- |
| **P0-1** | **职业页/天赋树按阶位懒渲染**：默认只渲染当前阶位（或首屏 N 张卡），其余滚动/点击阶位时再实例化；`data-search` 全文属性保留，搜索命中后再实例化 | 法师页 27k → <3k DOM、1.6 s 长任务 → <200 ms；**每次导航遗留垃圾按比例下降约 10 倍**（直接掐断根因 1） | 中（筛选/搜索/导航联动需改造） |
| **P0-2** | **主进程加崩溃与无响应恢复**：`render-process-gone` → 自动 `reload()` 并提示"页面已恢复"；`unresponsive` → 提示并提供重载按钮 | **白屏从"只能重启软件"变成秒级自愈** | 低 |
| **P0-3** | **页面卸载主动瘦身**：`pagehide` 时清空主体 DOM、解绑全局监听与大对象引用 | 遗留垃圾从"2.7 万节点"降到接近 0，即使不 GC 也不占内存 | 低 |
| **P0-4** | **站内搜索加防抖**（200 ms）+ 高亮只重算可见卡 | 每次按键阻塞 24~46 ms → 基本无感；顺带减少游离高亮节点 | 低 |
| **P0-5** | **创建页 iframe 预览用后销毁**（`iframe.remove()` 替代 `src='about:blank'`） | 单次预览峰值 -80~120 MB | 低 |
| **P0-6** | **更新策略调整**：`autoDownload=false`（提示后下载）、检查推迟到启动后 60~120 s、重启前确认 | 消除"开软件即下载 100 MB + 静默重启" | 低 |
| **P0-7** | **hash 定位瘦身**：跨文档定位改 `behavior:'auto'` 即时到位（或即时 + 短距平滑）；去掉重复的第二次 `scrollTo`；高亮动画换不触发布局的属性并缩短；祖先 `<details>` 只在必要时展开 | 跳转额外开销 -300~400 ms，长任务从 1,050 ms 降下来 | 低 |
| **P0-8** | **跳转反馈**：点击搜索结果立即显示"正在打开…"轻量遮罩（首页内），到位后自动消失 | 1.9 s 白等变成"有反馈的等待" | 低 |
| **P0-9** | **多窗口限流**：创建页「↗ 新标签页打开」限制同时存在的职业页窗口数（如 ≤2）或在打开前提示；长期可并入 P1-1 的同页预览 | 避免"点几次技能树 = +500 MB"（实测单窗口 +1 渲染进程约 90~170 MB） | 低-中（交互变化需确认） |

### P1 —— 削减根因 3 的燃料

| # | 改动 | 预期收益 |
| --- | --- | --- |
| **P1-1** | **减少"首页 ↔ 职业页"整页往返**：首页搜索结果直接在当前页用 iframe/浮层预览技能（复用创建页已有的 ov-viewer 能力），或把职业页做成同页切换而非整页导航 | 一次"查一个职业"不再重解析 3.82 MB 索引 |
| **P1-2** | **搜索索引按需加载/分片**：首页改为首次输入关键词时才加载索引（或按职业分片） | 首页不再每次解析 3.82 MB |
| **P1-3** | **内存压力兜底**：主进程用 `app.getAppMetrics()` 监控渲染进程 RSS，超阈值（如 1.2 GB）时提示 + 自动重载 | 兜住极端路径，避免再次白屏 |
| **P1-4** | `panel_data.js`（3.55 MB）拆分/懒加载 | 角色面板首屏 -100~250 ms |
| **P1-5** | `localStorage` 全量 `JSON.stringify` 写入节流（5 处同步写） | 编辑/加点不再同步卡顿 |
| **P1-6** | 注入脚本合并为一份（每次导航省 62 KB 解析 + 3 次 readFileSync/executeJavaScript） | 降低导航开销 |

### P2 —— 结构性

| # | 改动 | 说明 |
| --- | --- | --- |
| P2-1 | **Electron 升级**（22 → 新 LTS 线，Chromium 108 → 130+） | 结构性收益最大、风险最高（NSIS 打包、electron-updater、`will-download`/`setWindowOpenHandler` 行为差异全要重测）；建议 P0/P1 发版稳定后单独立项试发版 |
| P2-2 | 内置"性能自检"入口（显示各进程内存 / DOM 规模 / 长任务） | 用户反馈可直接带数据 |
| P2-3 | 测试页不入包（`职业页/_monk_test_top.html` 等） | 减体积、减门禁扫描面 |

1. **第一轮（当天可回归）**：P0-2 崩溃恢复 + P0-4 搜索防抖 + P0-5 预览销毁 + P0-6 更新策略 + **P0-7 hash 定位瘦身 + P0-8 跳转反馈** —— 全是低风险改动，能立刻消除"白屏""打字卡""点搜索结果卡死"三个最痛体验。

4. **第四轮**：按需推进 P1-4~P1-6、另行评估 P2-1 Electron 升级。

## 七、附：可复现的事实清单

- 用户运行的是 **v1.0.7278**（asar 内 `package.json` 版本，打包 `main.js` 与仓库字节数一致 27,867 B）→ 诊断结论直接适用于线上版本。
- 用户实例闲置 1.5 h：307 MB / 累计 CPU 约 30 s → **闲置不烧 CPU**，卡顿全部来自页面加载与导航。
- 系统缓存/临时文件不构成瓶颈；问题完全在渲染进程的 DOM 规模与回收时机。
