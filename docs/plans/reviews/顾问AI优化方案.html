[Snode] 顾问 AI：现状诊断与 6.0 优化方案

2026-11-08 · 顾问 6.0 方案 · 面向产品讨论与前后端实现评审

核心定位已确认：顾问不做「全能 AI DM」，只做「可溯源、可评测、可维护的规则与构筑助手」。 本文诊断来自 2026-11-08 当前工作区实测；六层结构与四个阶段是实施建议，尚未落地；配图均为方案示意，不是已实现界面。

1.背景

1.1 顾问已经不是「一个聊天框」

它现在有四个入口、两套运行时、一张 8.8 MB 的知识底座：

  • 入口：角色面板悬浮球、建卡页气泡、全屏聊天页（顾问.html）、手机端。
  • 运行时：桌面端在 Electron 主进程里直接 import 管线（scripts/mage-advisor.mjs）；移动端走阿里云 FC（advisor-server/server.js），Key 只在服务端。
  • 底座：advisor/ 8.8 MB —— 技能索引 5.5 MB、世界观 392 KB、进阶 728 KB、专长 183 KB，其余是车卡、装备与规则表。
  • 代码：54 个 advisor-*.mjs，13,856 行；另有 48 个 validate-advisor-*.mjs 与 23 个 build-advisor-*.mjs。

一次问答实际经过六步：规划 → 澄清闸门 → 分层检索 → 上下文装配 → DeepSeek 生成 → 引用清洗。理解这个顺序很重要，后面四个问题全都出在这条链上，而不是「资料不够」。

1.2 问题不在「缺内容」，在「喂不对」

5.0 审计已经给出结论：问题类型与检索能力不匹配。今天复测，这个判断仍然成立，而且可以量出来了：

1.3 为什么不再「一题一修」

过去五个版本的做法是：一条真实提问答错 → 加一个正则、一个工具、一段 prompt、一个 batch 用例。24 个 batch、38 个 intent、48 个 validate 脚本，就是这套方法的产物。

它有效，但边际收益在下降：

  • 每加一个能力要同时动四处（路由 / 工具 / 提示词 / 用例），漏一处就是线上回归；
  • 同类问题换个说法仍然可能漏，因为检索是字面匹配，不是语义匹配；
  • 回归面越来越大，但每条用例只锁定「这一版改的那道题」，无法回答「整体能力是变强还是变弱」。

2.诊断：四个结构性问题

2.1 检索是「字面包含」，不是检索

检索打分只有两行核心逻辑：把问句切成汉字与二元词，然后判断文本里是否包含这个词。

// scripts/advisor-retrieve.mjs:182
export function scoreText(queryTokens, text) {
  const hay = String(text).toLowerCase();
  let score = 0;
  for (const t of queryTokens) {
    if (hay.includes(t)) score += t.length >= 2 ? 3 : 1;
  }
  return score;
}

全仓 grep -i "embedding|cosine|vector|bm25|rerank" 结果为 none：没有向量、没有 BM25、没有重排。别名与同义词靠手写清单（STYLE_NAMES、tokenize() 里的关键词数组）硬补。

后果很具体：用户说「肉盾」「脆皮法师」「怎么堆命中」这类口语，字面命中不到任何条目；而「法师和吟游诗人有哪些相同技能」之所以能答对，是因为有专门的交集工具，不是因为检索好。

2.2 路由是正则表，实体解析有三套

38 个 intent 由 INTENT_RULES 的正则顺序抢答；分类器只在置信度 ≥ 0.65 时覆盖。更麻烦的是同一个实体名在不同模块各有各的解析：

位置职责认识「飞贼」吗
advisor-advancement-resolve.mjs进阶名解析认识（读 advancements.json）
advisor-class-l2.mjs · matchClassNameFromQuery职业名识别不认识，只认职业
advisor-clarify.mjs澄清闸门不认识 → 直接追问「你想玩哪个职业」

今天的现场复现：问「我想玩飞贼，我该怎么安排我的成长路线？」，线上直接返回「为了给你更准确的规划，请先补充一个关键信息：你想玩哪个职业？」；而同一条问句走 --dry-run、跳过澄清后，检索上下文里已经有游荡者与飞贼。

结论：闸门用最弱的解析器做了最强的拦截。这不是模型问题，是顺序问题——澄清应该发生在实体解析之后，只对「解析后仍然缺」的信息追问。

2.3 上下文又大又贵，且前缀不稳定

实测一次问答：输入 10,374 token、输出 443 token，其中只有 1,024 token 命中 DeepSeek 的前缀缓存（约 10%）。原因不是缓存不工作，而是前缀每次都在变：系统提示按 intent 选 profile 与 addon，证据块顺序随查询变化，用户问题在最前面。

DeepSeek 的上下文缓存按「相同前缀」命中，官方文档写得很清楚：重叠前缀只从缓存取，算作 cache hit。这意味着——把稳定内容放前面、把变化内容放后面，是免费的优化；现在的拼装顺序恰好相反。

2.4 质量闭环只到「检索层」

44 条 eval 全部是上下文断言（--context-only），不调 API，所以能在 CI 里跑得很快——这是优点。但它只能证明「证据进了上下文」，不能证明：

  • 答案里的数字是不是来自证据（编造 15 级门槛这类问题测不出来）；
  • 引用是否与正文一致（现在只清洗最后一行【参考】，正文里的行内引用不管）；
  • 结构是否符合该 intent 的作答契约（六段式缺一段也不报警）。

48 个 validate 脚本按版本批次组织，跑的是「这一版改的东西没坏」。要回答「能力矩阵有没有退化」，需要另一套组织方式。

3.目标与原则

3.1 三个可验收的目标

可溯源

答案里的每个数字、技能名、等级节点都能指回一条证据（[E12]），引用可点击跳转；指不回去的，不许出现在正文里。

可评测

用「能力矩阵」替代「版本批次」：12 个问题族 × 3 层检查，每次发版给出同一张表上的前后对比。

可维护

新增一个能力 = 改一行路由表 + 加一条用例；不再同时改正则、工具、提示词和 batch 脚本。

3.2 五条原则

  1. 结构化的交给函数，语言的交给模型。5.0 的判断继续成立，但要把「预先算好塞进上下文」升级为「模型按需调用」——前者只能覆盖预想到的问题，后者才能处理复合问句。
  2. 先测量再优化。没有 trace 的改动不合并；每次改动的收益要能用同一把尺子量出来。
  3. 一次只换一层。检索、路由、工具、装配分开上；每层都能单独回滚，出问题能定位到层。
  4. 离线可用优先。新增依赖必须能在断网时降级；顾问不能变成「必须联网才有用」。
  5. 不引入 Python 运行时。RAGAS、Guardrails 只借指标定义与校验器形态，本地用 JS 实现，避免打包链路多一套解释器。

3.3 非目标（本次明确不做）

  • 不 fine-tune、不训练自有模型；
  • 不引入独立向量数据库服务；
  • 不做对外 MCP server，工具先只做内部 JSON Schema；
  • 不做 AI DM 自动裁决——规则判定仍以主持人结算为准；
  • 不推倒重写 54 个脚本，按能力矩阵逐步收敛。

4.方案：六层结构

核心变化只有一句话：把「一张正则表 + 一次检索 + 一段拼接」改成「一台路由器 + 一个混合检索器 + 一组可调用原语 + 一个校验器」，并用 trace 与能力矩阵把它们串成闭环。

4.1 路由：一张表、一个解析器、一个分类器

38 个 intent 收敛为 12 个问题族。族是「同一种回答形态 + 同一套工具 + 同一个预算」，intent 只是族内的小分支，不再各自维护正则。

4.1.1 路由表长什么样

// advisor/routes.json（示意，字段会在 P1 定稿）
{
  "id": "build_roadmap",
  "family": "D",

三件事被这张表统一了：谁触发、需要什么实体、用哪些工具与多少预算。澄清闸门改为读取 entities.required，并且在实体解析之后才判断缺什么——「飞贼」能被解析成游荡者，就不再追问职业。

4.1.2 实体解析只留一个入口

新增 resolveEntity({ type, name })，覆盖职业 / 进阶 / 技能 / 装备 / 状态 / 专长六类，长名优先、别名兜底。现有三套实现先做适配层，双跑比对结果一致后再删除旧实现。验收标准很直接：同一条问句在路由、澄清、检索三处解析出的实体必须完全相同。

4.2 检索：从字面到混合

保留现有字面检索作为「零依赖兜底」，在其上叠三层，按成本从低到高排序：

层做法解决什么
L1 改写别名表 + 同义词 + 口语映射（「肉盾」→ 坦克/前排/防御）口语化、错别字、行话
L2 倒排对 chunk 建 BM25（含字符二元组），按词频与长度归一长文档里「提到但没排前面」的条目
L3 向量可选包：构建期产出向量，查询期一次 embedding；关闭时自动跳过换一种说法、语义相近但字面不重叠
融合RRF（Reciprocal Rank Fusion）合并多路结果，再按族预算截断避免单一召回源主导

切块不再是「一段正文」，而是带语境头的条目：职业·阶位·风格·来源·条目 id。这直接借鉴了 Anthropic 的 contextual retrieval——让每一块自带「它是谁的一部分」，否则「飞贼」这种词在进阶表、技能表、心得节点里各出现一次，检索分不清。

索引在构建期产出，manifest.json 记录源文件 sha256 与条目数；运行时校验哈希，过期就报警并降级。索引不进 git，随发布包构建，避免仓库再涨几十 MB。

4.4 装配：稳定的放前面，变化的放后面

4.5 校验：让「编造」过不了闸

现有清洗函数 sanitizeCitationLine 只处理回答末尾的【参考】行：id 不存在就按名称反查，查不到就剔除。这挡住了「引用假条目」，但挡不住正文里编造的数字。补齐三类检查：

检查怎么查失败时怎么办
结构按族的作答契约检查章节是否齐全（如 roadmaps 六段）缺章节 → 一次补写，只补缺的段落
事实抽取答案中的等级、数字、技能名、专长名，归一化（全半角/中文数字）后与证据集合比对不在证据中 → 标记「未收录」，不许进正文；必要时补检索一次再答
引用行内 [E3] 与末行【参考】都必须存在于证据 id 集合剔除无效引用；正文因此失去支撑的句子一并降级

这套「先查再答」的做法，对应 Self-RAG 的自我反思与 CRAG 的纠正性检索：检索不足时补的是证据，不是重写答案。重试只允许一次，避免把延迟拖成两倍。

4.6 评测：从「版本批次」到「能力矩阵」

用例库从 44 条扩到 200 条，按 12 族分层。来源有三个：现有 44 条（保留）、反馈队列里的真实问句（脱敏后）、每族按模板补齐的边界问法（未收录、多意图、跨职业、断网）。每条带 capability 标签，跑完自动生成矩阵：

指标现状（2026-11-08）目标定义
检索命中率43 / 44（97.7%）≥95%（200 例）金标条目出现在上下文
引用有效率0 错误（仅末行）0（行内 + 末行）引用 id 全部存在于证据集合
数字落地率未测≥98%答案中的数字能在证据中找到出处
结构符合率未测≥95%该族的契约章节齐全

现状值来自今天的实测（附录 A）；「未测」表示当前没有这项检查，不代表没有问题。

4.7 观测与成本

每次问答落一条 trace，六段各一个 span，字段固定：family、intent、toolCalls、inputTokens、cachedTokens、outputTokens、latencyMs、verify。默认采样 10% 写 tmp/advisor-traces/，可选导出 OTLP；trace 里不写角色名与用户问句原文，只留哈希与分类。

成本上有两个立竿见影的动作：

  • 前缀稳定化（§4.4）：同一族内系统提示与静态规则字节不变，缓存命中率从 10% 往上走，输入侧实际计费 Token 显著下降；
  • 语义缓存：只对「无快照、首轮、A/B/H 族」生效；键 = 归一化问句 + corpusHash + promptVersion，相似度 ≥0.95 且 TTL 7 天。命中时在界面标注「缓存」，并允许用户强制重答。

有快照、多轮追问、涉及时效的问答不缓存——这类问题一旦答错，比慢更糟。

4.8 双端统一：一个 core，两个适配层

现在桌面端与 FC 各自 import 同一套脚本，但装配方式不同、日志不通。改成 advisor-core（纯 ESM，不依赖 Electron）：

  • 桌面端：主进程 import core，IPC 只做参数搬运；
  • 移动端：FC 只做 HTTP/SSE 适配，不复制任何业务逻辑；
  • /api/health 返回 pipelineVersion + corpusHash + indexVersion；客户端版本不一致时提示「顾问数据版本不一致」，而不是静默降级。

排期原则：先有尺子，再改东西。P0 不做任何检索算法改动，只把「看不见」变成「看得见」；P1 才开始动检索与路由，此时每一步都有前后对比。每阶段独立发版、独立回滚，不合并成一个大版本。

主要风险

  • 路由表覆盖不全 → 旧规则保留一个版本做 fallback，双跑 diff 清零再切；
  • 工具循环拉高延迟 → 只对复合问句开放，超时直接降级为快路径；
  • 校验误杀 → 先跑 warn 模式一周，统计误报率再开 block。

怎么判定成功

  • 200 条用例的矩阵整体上移，而不是某一条从红变绿；
  • 同样的问题，输入 token 下降、延迟不升；
  • 新增能力的改动面从「四处」降到「两处」。

6.验收：可观察的行为

不验收「架构图画得对不对」，只验收下面八条能直接复现的行为：

  1. 「我想玩飞贼，怎么安排成长路线」不再追问职业，直接给出游荡者 → 飞贼的路线（今天会追问）。
  2. 「生命与丰收之神有哪些领域技能」的检索上下文包含该领域条目（今天 ctxMissing）。
  3. 同一问题两分钟内再问一次，输入 token 下降 ≥40%，界面标注「缓存」。
  4. 答案中出现的每个数字都能在证据中找到；找不到的被拦下或明确标注「未收录」。
  5. 行内引用与末行【参考】的每个 id 都在证据集合中，点击能跳转。
  6. 200 条 L1 用例全绿且 <30 s；L2 失败阻断发版。
  7. 断网时顾问降级为字面检索，并在界面明确标注「检索降级」，不静默。
  8. 桌面与 FC 的 pipelineVersion / corpusHash 不一致时，健康检查报警。

7.本次不做

  • 不做 fine-tune，不训练自有模型；
  • 不引入独立向量数据库或 Python 服务；RAGAS / Guardrails 只借指标与校验器形态；
  • 不做对外 MCP server——工具先内部化，等有第二个消费方再谈协议；
  • 不把 48 个 validate 脚本一次性重写，按能力矩阵逐批合并；
  • 不做 AI DM 自动裁决，规则判定仍以主持人结算为准；
  • 不做多模型自动路由（P3 之后再评估）。

8.参考：成熟方案取什么、不取什么

下面这些是业界已经跑通的做法。我们只取与「可溯源 + 可评测 + 零构建」相容的部分，不整体引入框架。

来源取什么不取什么 / 为什么
Anthropic · Building effective agents把「路由 / 并行 / 编排-执行 / 评估-优化」当工作流，而不是默认上自主 agent；能一步做完就不要循环不照搬自主 agent 的开放式循环——顾问的问题有明确答案边界
LangGraph用状态图描述路由与分支、每步可检查点可回放不引入框架依赖；Electron 内只需要一个轻量状态机
DSPy用数据挑 prompt 与 few-shot，而不是手调措辞不引入 Python 依赖；用现有 golden 集做离线对比即可
promptfoo声明式用例 + CI 门禁 + 多模型矩阵对比的形态不替换现有 runner，先把用例格式统一，再考虑嫁接
RAGASfaithfulness / answer relevancy / context precision 三个指标的口径不作为 CI 依赖；本地实现轻量版本
Langfusetrace → 数据集 → 回归的组织方式不自建平台；先本地 JSONL，需要时再导出 OTLP
OpenLLMetryGenAI span 的字段命名，避免自造日志格式暂不部署 collector
GPTCache语义缓存的键设计、相似度阈值与失效策略不做全量缓存；只对无状态问答开，且必须可强制重答
Guardrails输出校验器的组织形态（结构 / 事实 / 引用）不引入 Python 运行时
RAG 综述（arXiv 2312.10997）naive → advanced → modular 的分层演进，对应本文六层不追求端到端可训练 RAG
Self-RAG · CRAG检索不足时补证据再答，而不是硬答或重写不做检索器联合训练
Lost in the Middle长上下文对中段信息不敏感 → 证据首尾优先—
Anthropic · Contextual Retrieval给每个 chunk 加语境头（它属于谁的一部分）不引入其 BM25+向量混合的具体实现
DeepSeek · Context Caching相同前缀命中缓存 → 稳定内容必须前置不依赖其长期行为，缓存只是优化不是正确性前提
MCP工具 schema 的标准化方向，为将来第二个消费方留口P3 之前不做，避免过早抽象
